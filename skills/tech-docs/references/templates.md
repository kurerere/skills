## 1. 架构方案设计 / RFC (Design Doc)

```markdown
# [RFC] 方案名称：一句话概括核心设计

## 1. 摘要与背景
- **背景**：解决什么问题，当前现状及痛点。
- **一句话结论**：采用方案 X，预估达成指标 Y。

## 2. 目标与非目标 (Goals & Non-Goals)
- **目标 (Goals)**：本期必须交付的能力与量化指标（如：p99 延迟降低至 50 ms，QPS 支持 5000）。
- **非目标 (Non-Goals)**：**明确声明本期坚决不做什么**，界定边界，防止范围蔓延。

## 3. 总体架构与核心链路
- **架构拓扑图**：Mermaid 架构图或数据流图。
- **核心交互时序**：Mermaid 交互时序图。
- **关键数据结构 / 表结构**：核心 Schema 定义与索引设计。

## 4. 备选方案对比与否决理由
| 方案 | 核心优势 | 致命短板 / 否决理由 | 结论 |
| :--- | :--- | :--- | :--- |
| 方案 A | 开发成本低 | 无法满足长连接高并发需求 | 否决 |
| 方案 B (采纳) | 吞吐高、支持水平扩展 | 架构较重，需引入 Redis 集群 | **采纳** |

## 5. 容量评估与性能规划
- **流量预估**：日常 QPS、峰值 QPS、并发连接数。
- **资源规划**：计算节点规格、内存用量估算、磁盘存储与保留周期。

## 6. 容灾、降级与限流预案
- **下游异常表现**：当下游超时/宕机时，本模块的具体表现（超时时间设定、降级默认值、熔断阈值）。
- **过载保护**：单机限流阈值及拒绝策略。

## 7. 实施排期与风险
- **上线步骤**：建表 -> 旁路双写 -> 灰度放量（10% -> 50% -> 100%） -> 彻底切流。
- **回滚预案**：各阶段回退判定阈值与执行命令。
```

## 2. 故障复盘 / 事故报告 (Post-mortem)

```markdown
# [复盘] YYYY-MM-DD 某系统某故障事故分析报告

## 1. 故障基本信息与影响面
- **故障定级**：P2
- **持续时间**：14:10 ~ 14:42（共 32 分钟）
- **MTTD（发现时长）**：5 分钟（14:15 告警介入）
- **MTTR（恢复时长）**：27 分钟
- **影响爆炸半径**：某接口错误率峰值达 18%，影响用户下单约 320 笔。

## 2. 分钟级时间线 (Timeline)
- **14:05**：工程师 A 发布 v2.4.1 代码，涉及连接池参数调整。
- **14:10**：指标异动，数据库连接池耗尽，接口响应延迟从 30 ms 飙升至 3000 ms。
- **14:15**：P1 告警触发，值班人员介入并建应急群。
- **14:22**：排查定位到新增配置将最大连接数误设为 5（原为 100）。
- **14:28**：决定紧急回滚至上个稳定镜像版本 v2.4.0。
- **14:38**：回滚镜像拉取并重启完成，观察连接数恢复正常。
- **14:42**：接口错误率归零，业务验证确认彻底恢复。

## 3. 根因分析 (Root Cause)
- **直接诱因**：版本发布中配置项 `max_connections` 被手误修改为 5。
- **深层机制根因（5 Whys）**：
  1. 为什么手误未被发现？缺乏参数有效性自动化校验与范围检查门禁。
  2. 为什么测试环境没测出来？测试环境并发低，5 个连接足以支撑单人手工测试。
  3. 为什么直接全量上线？发布流程缺乏灰度分批观察期。

## 4. 应急止血处置
记录当时采取的临时处置操作、执行人、执行命令及止血效果。

## 5. 改进措施 (Action Items)
| # | 改进项内容（具体工程防范动作） | 负责人 | 预期完成时间 | 验证方式 |
| :- | :--- | :--- | :--- | :--- |
| 1 | 配置中心增加连接池下限校验门禁（不得低于 20） | 张三 | 2026-11-15 | PR 合入与测试 |
| 2 | 发布流水线强制要求 10% 灰度观察 15 分钟 | 李四 | 2026-11-20 | 流程上线演示 |
| 3 | 补充连接池打满告警策略，阈值设为 80% | 王五 | 2026-11-12 | 告警拨测模拟 |

## 3. 操作手册 / 部署 SOP (Runbook)

```markdown
# 某系统部署与操作手册

## 1. 适用范围与前置条件
- **系统与硬件**：SylixOS 2.3+ / Linux x86_64、ARM64；内存 ≥ 4 GB。
- **依赖工具**：Docker 24.0+，Python 3.10+。
- **网络与权限**：必须具备 `sudo` 权限，需开放 8080 与 9000 端口。

## 2. 部署与执行步骤
### 步骤 1：拉取并准备配置
```bash
git clone https://example.com/repo.git /opt/app
cd /opt/app && cp config.example.yaml config.yaml
```

### 步骤 2：启动服务
```bash
./bin/service --config config.yaml
```
期望输出：
```text
2026-11-09T17:00:00Z [INFO] Service listening on 0.0.0.0:8080
```

## 3. 状态验证（双向判定）
- **正向生效判定**：
  执行 `curl -s http://127.0.0.1:8080/health`，返回 `{"status":"UP"}` 即表示启动成功。
- **逆向失败判定**：
  若返回 `Connection refused`，检查日志 `tail -n 20 /var/log/app.log`；若包含 `address already in use`，说明端口被占用，执行 `lsof -i:8080` 查看冲突进程。

## 4. 回退与应急处置
- **备份位置**：配置文件备份在 `/opt/app/config.yaml.bak`。
- **回滚命令**：
  ```bash
  ./bin/service stop && cp config.yaml.bak config.yaml && ./bin/service start
  ```
- **不可逆操作标记**：清理缓存命令 `rm -rf /opt/app/data/*` 为**不可逆操作**，执行前必须确认数据已落盘。
```

## 4. 技术验证 / 压测报告 (Verification Report)

```markdown
# 某组件高并发性能验证报告

## 1. 结论（一页内概括）
**验证结论：通过。**
在 4 节点集群、2000 QPS 持续压测 60 分钟条件下，服务可用性为 99.99%，p99 延迟为 38 ms（达标线 ≤ 50 ms），未发生内存泄漏。

## 2. 验证基准与环境
- **机型与规格**：8C 16G，Ubuntu 22.04 LTS，Linux 5.15 内核。
- **版本信息**：服务版本 v2.3.0，压测工具 wrk 4.2.0。
- **测试模型**：同机同数据集，模拟 70% 读 + 30% 写混合流量。

## 3. 详细实测数据
| 并发连接数 | 压测 QPS | p50 延迟 | p90 延迟 | p99 延迟 | CPU 峰值 | 错误率 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 100 | 1000 | 12 ms | 18 ms | 25 ms | 28% | 0.00% |
| 500 | 2000 | 18 ms | 27 ms | 38 ms | 55% | 0.01% |
| 1000 | 3500 (拐点) | 35 ms | 65 ms | 120 ms | 88% | 0.45% |

## 4. 极限拐点与异常表现
- **性能拐点**：当并发上升至 1000（QPS 超过 3200）时，CPU 使用率超过 85%，p99 延迟急剧恶化至 120 ms。
- **资源泄漏监测**：持续压测 6 小时，进程 RSS 稳定在 180 MB ± 5 MB，无内存泄漏。

## 5. 建议与后续
建议线上单机负载限流阈值设定在 2500 QPS，超过阈值触发排队或快速失败。
```

## 5. 接口文档 / API 说明

```markdown
# 订单查询接口说明

## 1. 概述与鉴权
- **用途**：根据订单号批量查询订单支付状态。
- **协议**：HTTPS POST / JSON
- **鉴权方式**：Header 携带 `Authorization: Bearer <TOKEN>`。

## 2. 快速开始（可直接复制执行）
```bash
curl -X POST https://api.example.com/v1/orders/query \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"order_ids": ["ORD_20261109_001"]}'
```

## 3. 请求参数
| 字段名 | 类型 | 必填 | 默认值 | 约束与说明 |
| :--- | :--- | :--- | :--- | :--- |
| `order_ids` | array[string] | 是 | - | 订单号列表，单次最多 50 个 |
| `include_details` | boolean | 否 | `false` | 是否返回商品级明细 |

## 4. 响应数据与错误码
**成功响应 (HTTP 200)**：
```json
{
  "code": 0,
  "data": [
    {
      "order_id": "ORD_20261109_001",
      "status": "PAID",
      "amount_cents": 12800
    }
  ]
}
```

**业务错误码**：
| 错误码 (code) | HTTP 状态码 | 含义 | 排查处理建议 |
| :--- | :--- | :--- | :--- |
| 10001 | 400 | 单次查询数量超限 | 拆分单次请求，保持在 50 个以内 |
| 10004 | 404 | 订单号不存在 | 确认 order_id 是否属于当前商户 |

## 5. 调用限制
单商户调用频次限流为 200 QPS，超限返回 HTTP 429。
```

## 6. 对外交付说明 / 发版说明 (Release Notes)

```markdown
# v2.4.0 版本交付与发版说明

## 1. 本次发布内容
- **新特性**：支持基于 Trace ID 的全链路日志检索；新增订单批量导出接口。
- **缺陷修复**：修复在 ARM64 架构下特定配置因字节对齐引发的 SIGBUS 崩溃。
- **破坏性变更 (BREAKING CHANGES)**：废弃旧版 XML 响应格式，强制仅支持 JSON。

## 2. 运行环境与依赖要求
- **系统要求**：Linux 64-bit (glibc ≥ 2.31) 或 SylixOS 2.3+。
- **兼容版本**：向上兼容 v2.2 及 v2.3 客户端；低版本客户端需升级 SDK。

## 3. 升级与回退指南
- **升级步骤**：替换二进制并执行数据库增量迁移脚本 `migrations/20261109.sql`。
- **回退步骤**：执行回退 SQL `migrations/20261109_down.sql`，还原旧版本程序。

## 4. 已知限制与临时规避
- **已知限制**：单次导出数据超过 10 万行时内存占用偏高。
- **规避建议**：建议通过 `date_range` 参数分天多次导出。
```

# 工程技术文档结构化表达规则

> **注**：微观语言风格、去 AI 味、大词白名单、专有名词大小写与盘古之白排版规范，完全遵从 [writing](file:///Users/wangjijie/.gemini/config/skills/writing/SKILL.md)。
> 本文件仅补充面向工程技术文档的**结构化表达与组织约定**。

---

## 1. 节标题与步骤命名
- **节标题必须使用动宾短语或明确的名词短语**：
  - ✔️ `配置网卡参数`、`启动核心服务`、`验证端口监听`
  - ❌ `网卡配置说明`、`接下来我们来启动服务`、`如何验证服务是否启动？`
- **步骤按顺序编号**：操作步骤使用 `步骤 1：...`，不搞层层嵌套的小标题。

## 2. 命令与配置块规范
- **给全完整命令，禁止口头代填**：严禁出现 `按实际情况修改`、`... 其余配置略 ...`。
- **标注语言类型**：Markdown 代码块必须显式标注语言（`bash`、`json`、`yaml`、`c`）。
- **长配置与模板必须内嵌**：读者需要复制的最小可用配置，全文直接内嵌，避免让读者跳出页面去外部下载。

## 3. 表格与段落的分工
- **表格承载多维度对比**：用于方案选型对比、API 参数表、错误码表、性能压测矩阵。单元格内写简短事实，不写大段叙述。
- **段落承载逻辑推理与因果分析**：不要把深层技术推理强行切碎塞进表格或单薄的清单里。

## 4. 图表的克制使用
- **只有当拓扑拓扑、时序交互用文字难以表达时才画图**：
  - 优先使用 Mermaid 格式（`graph TD`、`sequenceDiagram`），代码化且易于 Git 追踪比对。
  - 拒绝无信息增量的纯示意图（如画一个“用户 -> 浏览器 -> 服务器”的空洞大方块）。

## 5. 全文术语一致性
- **一个概念全文只使用一个名称**：
  - 严禁在同一篇文档中混用 `连接池`、`链接池`、`Connection Pool`。
  - 缩写在正文中首次出现时必须带全称，如 `MTTR（平均恢复时长，Mean Time To Recovery）`。

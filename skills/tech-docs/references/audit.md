# 交付前自查清单

交付前逐条核对，全部符合才算达到交付标准。

## 1. 事实与证据核对
1. **命令与环境实测**：每条命令、每个参数都在目标环境执行过？未实测的是否已按 `> [!WARNING] **待确认**：...` 规范标记或移出操作步骤？
2. **数字与配置真实**：每个性能数据、版本号、路径都来自实际系统输出或配置文件，而非记忆编造？
3. **一份文档走到底**：读者只用这一份文档，能否从第 1 步顺畅走到目标？是否存在隐含的外部口头知识依赖？
4. **证据与正文分离**：大段原始日志、测试数据是否已收敛至附录或 `.evidence/` 目录？正文是否仅保留结论？

## 2. 结构与场景核对
5. **按动作排序**：章节是否按读者操作的时间先后排序？任意抽掉一章，后续章节是否会因此失效？
6. **边界与 Non-Goals**：方案类文档是否明确声明了“本期不做什么”？
7. **复盘 Action Items 落地**：复盘报告中的改进项是否都有明确的技术防范动作、责任人和预期完成时间？是否存在口号式表达？
8. **双向判定与回退**：操作步骤中是否同时给出了“正向生效判定”与“逆向失败报错特征”？

## 3. 高风险操作专项核对
凡涉及修改系统核心配置、覆盖文件、数据库变更、线上服务重启、删除数据：
- 操作前是否有明确的备份命令，且备份路径可查？
- 是否有验证过的可执行回退命令（而不是写“联系运维”或“重装系统”）？
- 是否对不可逆操作（如数据清理、删除分区）显式加粗警告？

## 4. 语言与排版（配合 writing）
- **通过 writing 规则自查**：是否已运行 `bash <SKILL_DIR>/../writing/scripts/check.sh <文档>`，并逐处处理命中？
- **专有名词大小写**：如 `GitHub`、`PostgreSQL`、`Kubernetes`、`Redis` 是否符合官方写法？
- **盘古之白**：中文字符与英文字符、数字之间是否都保留了 1 个半角空格？
- **无 AI 废话套话**：文末是否已剔除“综上所述/结合业务场景选择”等无信息增量的总结段？

## 反模式对照表

| 反模式 | 典型现象 | 正确处理方式 |
| :--- | :--- | :--- |
| **背景铺垫过长** | 开头大篇幅讲行业背景与概念演变 | 删掉，第一句直接给读者目标或核心结论 |
| **虚假对称列表** | 对比方案时硬凑“3 优 3 缺” | 给出当前业务最看重的主指标，指出弃用方案的致命短板 |
| **自证式叙述** | “我试了 A，又试了 B，最后发现……” | 改为“已验证：A 可行；B 失败，原因为……” |
| **未验证写成确定** | “生产环境通常需要配置参数 X” | 实测后确定，或标明 `> [!WARNING] **待确认**：生产参数需压测` |
| **免责式收尾** | “以上步骤仅供参考” | 明确写清适用版本与边界条件，删掉免责空话 |
| **隐藏失败分支** | 只写成功路径，读者遇错茫然 | 补充“常见错误与逆向判定” |

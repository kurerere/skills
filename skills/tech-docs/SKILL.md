# 工程技术文档规范

文档质量不取决于篇幅与文字多寡，而取决于读者能否照着做成事。以下五条不变量任一违反，文档即不合格。

## 五条不变量

1. **先查事实，后落笔。** 事实性陈述必须有可靠来源。优先级：本环境实测 > 目标版本官方文档 > 同版本他人案例 > 推断。推断绝不直接作为事实进入正文。
2. **按动作排序，不按知识点排序。** 章节顺序等于读者完成目标的先后顺序；读者不需要先理解全套原理才能执行第一步。
3. **密度由读者路径决定。** 只保留“读者不做就会失败”的信息。非必要背景进附录或直接删除。
4. **不确定性显式标注。** 未经验证的内容禁止使用确定语气掩盖，按标准语法显式声明。
5. **不美化结果与缺陷。** 已知限制、未解决问题、失败分支如实记录，并给出回退或替代路径。

## 不确定性三档标准写法

全文按三档标注置信度，统一采用标准化 Markdown 语法：

| 档位 | 依据 | 正文写法规范 |
| --- | --- | --- |
| **已验** | 目标环境实测输出 | 直接陈述，无需特殊标记 |
| **据文档** | 官方手册或规范，未在当前环境实测 | 行内明确标明出处，如：`（依据：官方手册 v2.4 第 3 章）` |
| **待确认** | 尚无可靠测试与官方依据，属于推断 | 统一使用引用警告块：<br>`> [!WARNING]`<br>`> **待确认**：ARM64 架构下暂未实测，可能需要额外补丁。` |

未实测的命令严禁直接混入主流程步骤，必须下沉到“前置检查”或作为“待确认风险”标注。

## 流程

### 阶段 0 定盘

动笔前明确四个核心要素，不明确不要盲目开写：

- **读者是谁，处于什么场景**：现场排障 / 架构评审 / 线上发布 / 外部客户交付。
- **目标是什么**：读者读完文档后要能做成什么事（动词开头，如“在 SylixOS 上启动 QEMU 模拟器”）。
- **交付形式**：默认单篇 All-in-one；只有使用场景完全割裂时才拆分（如“操作部署手册”与“对外脱敏白皮书”）。
- **非目标 (Non-Goals)**：明确本次文档或方案**坚决不做什么**，界定边界。

### 阶段 1 取证（Agent 动作指引）

技术文档拒绝靠记忆瞎编，优先从机器和仓库取事实：

- **环境与版本取证**：运行 `cat /etc/os-release`、`uname -a`、`git describe --tags` 或检索 `package.json` / `go.mod` / `Cargo.toml` 锁定确切版本。
- **路径与默认配置**：直接读取本地配置文件或代码常量，禁止凭印象编造“默认端口 8080”或假路径。
- **命令副作用验证**：先确认命令的前置条件、权限要求（是否需要 `sudo`）及不可逆后果。
- **原始凭证归档**：大段原始终端输出、日志切片、测试原始数据统一存放在项目内 `.evidence/` 目录或附录中，正文只保留提炼后的结论和最小调用示例。

### 阶段 2 搭骨架

按文档类型直接套用标准模板，详见 [references/templates.md](references/templates.md)。
- 骨架自检：从头读到尾，任意抽掉一章，后续章节是否会因此无法执行？不会失效的章节就是多余章节。

### 阶段 3 写作与语言

- **语言规则严格遵从 [writing](file:///Users/wangjijie/.gemini/config/skills/writing/SKILL.md)**：先有落点再写句子、数据大于解释、盘古之白排版规范、拒绝 AI 废话套话。
- **结构化表达规范**见 [references/register.md](references/register.md)：节标题使用动宾短语（“配置网卡参数”），命令与配置给全，表格承载对比，段落承载推理。

### 阶段 4 删减裁撤

逐段审问三道关卡，任一答案是负向就坚决删除：

1. 读者不做这件事会不会失败？（不会 $\rightarrow$ 删）
2. 删掉这句话，读者会不会做错？（不会 $\rightarrow$ 删）
3. 这句话是帮读者做事，还是在证明“我懂得多 / 我做过”？（后者 $\rightarrow$ 删）

### 阶段 5 交付前自查验收

交付前对照 [references/audit.md](references/audit.md) 逐条核对验收。任一条不达标，不交付。

### 阶段 6 维护更新

- 读者卡在某处 $\rightarrow$ 增补进“常见错误与解决”，不直接散落篡改主干流程。
- 环境变化 $\rightarrow$ 修改前置“适用范围”，严禁用“以上仅供参考”推卸责任。

## 高风险操作强制规范

凡涉及修改系统核心配置、覆盖文件、数据库变更、线上服务重启、删除数据：
1. 必须在执行前给出明确的**数据备份命令**（备份路径必须显式可查）。
2. 必须给出**可执行、可验证的回退步骤**（拒绝“出现异常请联系管理员”或“重装系统”）。
3. 必须对**不可逆操作**（如 `rm -rf`、物理 drop 表、固件擦除）显式加粗警示。

## 与其他技能的分工与协同

- **语言修辞与去 AI 味** $\rightarrow$ 全权接入 [writing](file:///Users/wangjijie/.gemini/config/skills/writing/SKILL.md)。写作时语言遵循 writing 的落点律、白名单与排版规范。
- **需求探索与共创** $\rightarrow$ 目标和读者诉求完全模糊时，先用 doc-coauthoring 引导对齐。
- **外部调研取证** $\rightarrow$ 资料不足时使用 research 调研，实测或核查官方文档后再落盘。

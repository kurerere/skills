# 工程技术文档

让读者能完成目标，或有依据地作出判断。先识别读者、使用场景和已有文档约定，再决定写什么、怎样组织。按任务规模取舍，不为填模板扩写，也不为精简删除必要的背景、限制和诊断信息。

## 事实与证据

**事实有来源，结论不超出来源能支持的范围。** 按问题选择目标环境结果、当前源码与配置、目标版本官方资料或用户明确给出的约束。来源冲突时核对版本、条件和要回答的问题，不套固定优先级。

区分已经观察到的结果、资料规定的行为、推断和拟议方案。可用自然语言、来源链接或项目既有标记表达，不要求每项都套警告块。未知项明确写出，示例、估算和目标值不能冒充实测值。

技术文档可以记录尚未实施的设计与验证计划。无法实测时交代依据、未验证范围及判定方式；写文档本身不构成执行部署、修改系统或触发外部操作的授权。

## 按读者任务组织

- 操作手册让前置条件、步骤、成功判定和失败处理连贯。
- 方案说明问题、约束、选择依据和代价；备选方案不必有“致命缺陷”才可放弃。
- 复盘分清影响、已确认的因果与未决问题，改进项说明如何落实；未知的负责人和日期不能编造。
- 接口文档说清调用条件、输入输出和错误行为；移植或验证说明区分构建通过、目标运行和实际覆盖范围。

需要类型参考时读 [文档类型与内容取舍](references/templates.md)，表达方式有疑问时读 [组织与示例](references/register.md)。参考是起点，章节、数量和形式由任务决定，不要求全部采用。

已有文档能满足读者时优先在原处更新，必要时链接权威来源。是否拆分以读者路径和维护成本为准，不要求全部内嵌，也不自动建立一套配套文档。

## 操作说明与交付

命令、路径、参数及预期结果应能对应目标环境。可变值标明由哪里取得；占位示例明确需要替换的部分，避免看似可直接执行的虚构配置。涉及数据丢失、服务中断或难以撤销的步骤时，说明对象、前置条件、具体影响和适用的恢复办法；无法恢复时如实说明。

保留支撑执行、理解和决策的内容，删除重复与无关信息。按当前任务核对 [交付自查](references/audit.md)，检查源材料与正文是否一致、读者路径是否完整、限制与未知项是否清楚。没有依据的部分标出，不用一句“仅供参考”掩盖。

原始日志和数据按项目约定存放，正文保留必要摘录与指路。没有归档要求时只保留任务所需材料，清理临时数据，不自行建立证据目录或修改忽略配置。

语言优先准确、具体和自然。已安装 `writing` 时可结合使用，从环境提供的实际位置读取；未安装不影响本技能使用。

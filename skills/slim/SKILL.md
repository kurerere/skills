# 主干文档：只写代码说不出来的

写给下一个会话的 AI：给出发点和方向，不给细节——细节它从代码现取。没有文档它会去查代码，文档写错它会照着错的做；所以宁可少写，不可写细。

## 写入前三问

一条信息想进长期文档，先过三问，有一问答不上就不写：

1. AI 只看代码能不能推出这条？能 → 不写。
2. 能不能写成测试、类型、lint 或 CI 检查？能 → 写那个，机器能验证的约束不进文档。
3. 过期那天谁会知道？答不上 → 不进长期文档，写进 commit message、PR 描述或 issue——随一次改动翻篇的地方。

## 什么算主干

只写 AI 从代码推不出、或会推错的东西：

| 类别 | 写什么 | 为什么代码说不出来 |
| --- | --- | --- |
| 意图 | 做什么、明确不做什么 | 代码只有现状，没有取舍 |
| 决策理由 | 为什么选 A | 代码只看得见选了 A |
| 否决项 | 放弃的方案及原因 | 不写，下个 AI 会再提议一遍 |
| 硬约束 | 不得改变的行为、对外承诺、兼容底线 | 测试未必拦得住 |
| 教训 | 踩过的坑、版本陷阱 | 代码里看不出来 |
| 指路 | 入口、权威来源在哪 | 一句话指路，不复制内容 |

分两档。意图、硬约束、指路必须照办；决策理由、否决项、教训是当时的判断，不是永久命令——它们防止重复提议已否决的方案，但不保证今天仍成立。与当前代码或新证据冲突时，指出冲突，不沉默服从。

## 什么不算主干

以下用时现查，不落盘：

- 文件清单、目录结构、函数签名、调用关系——现 grep 一遍比抄进文档准
- 接口字段表、配置项全表——代码是唯一权威
- 实现步骤、任务拆解、进度——写完即过期
- 探索过程——留在 commit message 和会话里
- 对代码行为的复述——两份副本必然分叉

判据：这段是帮 AI 对齐方向，还是帮它省得再查？后者不写——省一次查，赌一次错。

## 落在哪

- 约束、指路、验证命令 → `AGENTS.md`（或项目既有约定文件）
- 决策与否决 → 决策记录（ADR 或项目既有位置）：一份一个决定，写清当时的依据
- 功能需求 → `refine-requirements` 的编号条目
- 设计稿、提案、spec → 短期材料，落地后归档或删除，不进长期文档
- 探索笔记、调试记录 → 会话内或 `.scratch/`，收尾时删除或提炼进 commit message

新增文档文件先回答：它和既有文档怎么分工？答不上就并进去，不开新文件。

## 主干文档的形状

读一遍不超过几分钟；长到需要目录，先怀疑混进了细节。够用的骨架：

```
## 意图   —— 做什么、不做什么
## 约束   —— 不得……、必须保持……
## 决策   —— 选了什么；否了什么，为什么
## 指路   —— 入口、权威来源、怎么验证
```

不是模板，是底线：缺一节会走错路，多出来的先怀疑。

## 保持干净

- 改动让既有文档某条过时时，在同一提交里改它或删它
- 会话中的笔记、草稿、调研记录，收尾时删掉、提炼成主干、或转成短期材料
- 某条已经能被代码或测试覆盖了，删文档、补验证

## 收尾自检

- [ ] 新增每段文档都能答出"代码为什么说不出来"
- [ ] 决策/否决/教训写清了当时的依据，不只是结论
- [ ] 没有文件清单、接口表、实现步骤、过程叙述进仓库
- [ ] 被本次改动推翻的文档条目已改或已删
- [ ] 仓库里没留下探索过程的文件
- [ ] 新增文件能答出分工

## 与其他技能的关系

- `refine-requirements`：需求条目是主干的一种，按它的模板和三态写
- `evidence-first-docs`：写给操作者的手册、SOP、交付说明按那份取证；这份管仓库里留什么
- `writing`：文档语言按那份写

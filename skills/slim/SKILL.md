# 主干文档：只留代码说不出的信息

写给下一个会话的 AI：给出发点和方向，不给细节——细节它从代码现取。没有文档它会去查代码，文档写错它会照着错的做；所以宁可少写，不可写细。

> **适用范围**：本技能仅用于仓库内长期协作文档（如 `AGENTS.md`、ADR、README 导引）。面向运维与外部的操作手册、部署 SOP 与接口文档按 [tech-docs](../tech-docs/SKILL.md) 编写，保持独立完整，不在此处删减。

## 写入前三问

一条信息想进长期文档，先过三问，有一问答不上就不写：

1. **AI 只看代码能不能推出这条？** 能 → 不写。
2. **能不能写成测试、类型、lint 或 CI 检查？** 能 → 写那个，机器能验证的约束不进文档。
3. **过期那天谁会知道？** 答不上 → 不进长期文档，写进 commit message、PR 描述或 issue——随一次改动翻篇的地方。

## 什么算主干

只写 AI 从代码推不出、或会推错的东西：

| 类别 | 写什么 | 为什么代码说不出来 |
| --- | --- | --- |
| **意图** | 做什么、明确不做什么 | 代码只有现状，没有取舍 |
| **决策理由** | 为什么选 A | 代码只看得见选了 A |
| **否决项** | 放弃的方案及原因 | 不写，下个 AI 会再提议一遍 |
| **硬约束** | 不得改变的行为、对外承诺、兼容底线 | 测试未必拦得住 |
| **教训** | 踩过的坑、版本陷阱 | 代码里看不出来 |
| **指路** | 入口、权威来源在哪 | 一句话指路，不复制内容 |

意图、硬约束、指路必须照办；决策理由、否决项、教训是当时的判断，防止重复提议已否决的方案，但不保证今天仍成立。与当前代码或新证据冲突时，指出冲突，不沉默服从。

## 什么不算主干

以下信息不落入长期主干，出现即删：

- **不写代码行号**：如 `见 service.go 第 45 行`，代码一改立刻失效。
- **不贴源码实现**：最多放调用命令、最小调用示例或函数签名，不贴完整函数体。
- **不列易变文件树**：用一句话指路（如“核心服务收敛在 `src/services/`”）。
- **不抄字段表与配置全表**：代码与配置文件是唯一权威，现查比抄进文档准。
- **不留过程流水账**：留在 commit message 和会话里。

判据：这段是帮 AI 对齐方向，还是帮它省得再查？后者不写——省一次查，赌一次错。

## 落在哪

### 1. 项目协作主干 → `AGENTS.md`（控制在 100 行内）
长到需要目录，先怀疑混进了代码细节：

```markdown
# AGENTS.md 最小骨架
## 1. 验证命令   —— 单行可跑的构建、测试、lint 命令
## 2. 意图与边界 —— 核心做什么、明确不做什么
## 3. 架构指路   —— 核心逻辑在哪个目录，入口文件是哪个
## 4. 硬约束     —— 不得触碰的底层兼容底线、协议标准
```

### 2. 重大决策与否决 → ADR
一份一个文件，4 行写清：

```markdown
### ADR-001: 决策标题（如：改用 Redis 管理分布式会话）
- **状态**：已采纳（或已否决 / 已废弃）
- **背景与依据**：遇到什么问题（如多节点部署内存会话无法共享）
- **决策**：选了什么方案
- **否决与代价**：否决了方案 X（原因 Y），代价是需额外运维 Redis
```

### 3. 其他分工
- 功能需求 → `refine-requirements` 的编号条目。
- 临时草稿、过程笔记 → 留存会话或 `.scratch/`，任务收尾时删除或提炼进提交信息。

## 保持干净与自检

- 改动让既有文档某条过时时，在同一提交里改它或删它。
- 某条已经能被代码或测试覆盖了，删文档、补验证。
- **收尾自检**：
  - [ ] 没有写死代码行号、没有大段粘贴源码实现
  - [ ] 没有文件清单、接口字段表进长期主干
  - [ ] 决策与否决项写清了当时依据，而非空洞结论
  - [ ] 被本次改动推翻的文档条目已改或已删
  - [ ] `AGENTS.md` 或主干索引可在单屏内读完（100 行以内）

## 与其他技能的关系

- `refine-requirements`：需求条目是主干的一种，按它的模板和三态写
- `tech-docs`：写给操作者、运维、外部的手册与 SOP 按其规范与完整骨架写；本技能只管代码仓内的长期协作主干
- `writing`：主干文档的微观语言与排版按那份写

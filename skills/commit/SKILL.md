# Git Commit

提交信息写给以后查看历史的人：标题说清改了什么，正文只补充理解这次变更必需的原因或影响。

## 确定操作与范围

- 先读当前项目的提交约定，沿用会话中已有的授权。仅起草或评审提交信息时，只输出文字；实际提交、amend 和 push 分别按已授权范围执行，提交请求本身不包含 push。
- 查看 `git status --short`、工作区与暂存区 diff，必要时读取目标未跟踪文件。用户指定文件、改动片段或已有暂存范围时，以该范围为准；其余情况只处理本次任务的改动。
- 保留无关的工作区和暂存改动，注意同一文件中混合的改动。范围明确就继续；只有无法确定归属或无法安全隔离时再询问。
- 普通提交没有目标改动时停止。用户要求或项目已有明确约定时可以 amend；信息应涵盖修正后整个提交，保留已发布历史。

只改最后一个提交的信息时，先读原提交内容，使用 `git commit --amend --only -F <消息文件>`，不传文件路径，以保留原提交树并排除已有暂存改动。需要改更早的提交时，先确认历史改写范围。

## 提交信息

格式依据 [Conventional Commits 1.0.0（约定式提交）](https://www.conventionalcommits.org/zh-hans/v1.0.0/)。中文和通常只写标题是本技能的偏好；用户指定的语言、格式与项目约定优先。

```text
type(scope): 摘要
```

- 新功能用 `feat`，修复 bug 用 `fix`；其余类型如 `refactor`、`docs`、`test`、`chore`、`perf` 按项目约定选择。`scope` 是可选的模块范围，使用项目认可的名称。
- 标题通常一句话，写具体动作和对象。多个文件服务于同一目的时概括共同变化；互不相关的改动按授权范围分开处理。
- API、命令和模块名保留原文。写实际行为，避免用“全面完善”“能力补齐”“增强稳定性”等措辞代替具体变化。
- 默认只有标题。重要原因、非显然的行为变化、兼容性边界或迁移要求确实需要说明时，再空一行写简短正文。破坏性变更用冒号前的 `!`（如 `feat(api)!:`）或大写脚注 `BREAKING CHANGE: 描述` 标记，并说明影响。
- 文件和函数清单、排查过程、测试汇报放在任务报告里；只有影响理解的性能数据、版本、提交引用等才进入提交信息。删掉不会影响理解的句子，以及与标题重复的正文。
- 默认不新增署名尾缀，用户或项目有明确要求时遵循。修正信息时保留原有的必要署名、引用和破坏性变更说明。

```text
fix(storage): 修复写入后的缓存失效
```

需要解释非显然取舍时：

```text
fix(storage): 改用定位读取访问文件页

既有映射在文件写入后可能保留旧数据，读取改为页缓存，写入后使相关缓存失效。
```

## 验证与交付

按当前项目要求验证受影响行为，可复用覆盖当前改动的已有结果。纯消息修改无需重跑代码测试；文档或配置选择相关检查。本次改动引入的失败先修复，环境受阻或无关失败如实报告。

执行前核对实际准备提交的 diff；仅改信息时核对原提交。多行信息写入临时文件并用 `-F` 传入。保留项目要求的 hooks 和签名配置，失败后检查状态再处理。

提交后核对实际内容与预期范围；仅改信息时确认提交树未变，原有待提交改动仍保留。简短报告提交 SHA、完整信息和实际验证结果；未运行的检查明确说明。仅起草时直接给出信息正文。

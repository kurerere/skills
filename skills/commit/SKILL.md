# Git Commit

提交信息写给以后查看 Git 历史的人。只保留本次提交的主旨，以及不能从标题直接理解的重要原因或影响。不要把 diff 清单、工作过程或验证报告搬进提交信息。

## 1. 确认提交范围

- 查看 `git status -s`、`git diff` 和 `git diff --cached`，必要时检查目标未跟踪文件。以实际准备提交的内容为依据。
- 没有目标改动则停止；仅修改已有提交信息时不受此限制。
- 用户已明确选择暂存范围时，只提交该范围，不擅自追加文件。
- 只暂存本次任务相关改动，不默认 `git add .`，不夹带用户已有的无关改动。范围无法确定时先询问。
- 仅在用户要求时使用 `--amend`。改写信息要涵盖原提交的完整变更；只改信息时不得带入其他暂存改动。不自动 push 或改写其他历史。

## 2. 按需验证

遵守项目要求，执行与改动相关的构建、测试或检查。验证失败先处理本次改动引入的问题；无关失败或环境阻塞如实报告，不擅自扩大修改范围，不将未验证写成通过。

纯提交信息修改无需重跑构建。文档或配置改动选择对应检查，不为凑流程执行无关测试。

## 3. 起草提交信息

### 默认只有标题

```text
type(scope): 中文摘要
```

- `type` 使用 `feat`、`fix`、`refactor`、`test`、`docs`、`chore`、`perf` 等规范类型；`scope` 使用准确的小写模块名。
- 中文摘要通常 12–28 字，写清“改了什么”，例如“修复……”“新增……”“移除……”。不要为了字数损失必要含义。
- 一次提交只有一个主旨；多个文件服务于同一目的时合并概括，不按文件逐项复述。
- 以中文叙述，API、命令、模块名等必要技术标识保留原文，不强行翻译。

### 只有标题不够时才加正文

仅在需要补充重要原因、非显然的行为变化、兼容性限制或迁移要求时添加正文。空一行，默认 1–3 条短列表，每条一句、尽量不超过 50 字。不为凑条数拆分同一件事，不重复标题。重大变更可适当展开，但只写读者必须知道的信息。

```text
fix(sylixos): 修复子进程退出时的资源泄漏

- 退出前释放尚未关闭的管道，避免重复创建进程耗尽资源
```

### 内容取舍

默认不写：
- 文件路径、函数名、修改处数、章节数、条目数等 diff 或正文中已有的清单。
- 测试命令、通过数、通过率、编译平台列表和“已验证”等验收汇报。
- 排查经过、方案尝试、用户要求、AI 工作过程和后续计划。
- 与本次改动无关的背景、未发生的改动或未经证实的效果。

这些信息不是一律禁止：版本兼容边界、关键性能结果、必要的提交引用等，确实影响理解时保留。判断标准是：删掉它，后来的人是否会误解这次提交或用错它？不会就删。

### 语言与署名

- 直接写事实，避免“全面完善”“统一收敛”“能力补齐”“闭环”“零变化”等空泛或生硬表达。
- 不写“提升可维护性”“增强稳定性”等缺少具体依据的总结。
- 不用连续括号、箭头串联或“模块名：……”排比堆砌细节。
- 不自动添加 `Signed-off-by`、`Co-authored-by`、`Assisted-by` 等署名尾缀，除非用户明确要求。修正信息时不擅自删除原有署名或项目必需的引用、破坏性变更标记。

发送或提交前再删一遍：标题已经说清的正文删掉；没有必要正文时，只留标题。

## 4. 提交与报告

提交前检查 `git diff --cached`，确保实际暂存内容与提交信息一致，再按用户要求创建或修正提交。

完成后简短报告：提交 SHA、提交信息全文、实际验证结果。未运行或受阻的检查明确说明。验证结果放在对用户的报告里，不机械写进 commit message。

## 简短示例

新增文档介绍各模块支持程度及限制，不复述测试统计和章节结构：

```text
docs(sylixos): 新增面向用户的 API 支持清单
```

更新文档内失效的提交引用，不罗列替换数量：

```text
docs(sylixos): 更新文档中的提交引用
```

默认到此结束，不再补“梳理分级、补充说明、明确边界”等同义条目。

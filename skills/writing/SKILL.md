# 写中文：先有落点，再写句子

这套规则只管语言，不管文档结构，不依赖其他技能。写文档时使用。

## 一条主规则

**先有落点，再写句子。**

落点是这句话能指到的东西：一个数字、一条命令、一次实验、一段代码、一个具体的人或物。

动笔之前手里没有落点，句子就会自己去找替代品。最顺手的替代品，是把两个抽象名词拼成一个新词。黑话不是文风问题，是没东西可写的时候用来填空的。

| 本来要说的 | 造出来的词 | 问题 |
| --- | --- | --- |
| 交出去之前自己过一遍 | 交付前门禁 | 中文里没有这个组合，读者得猜 |
| 判断哪些该留、哪些该删 | 密度裁剪 | “密度”“裁剪”都是比喻，落不到具体的东西上 |
| 说清为什么不选另一条路 | 成对取舍 | 同上 |
| 图和章节对得上 | 结构自咬合 | 借了牙科的词 |

这四个词拿去搜，一条命中都没有。真词不会这样。

## 动笔之前，先把落点列出来

写之前列一张单子：这次要用的数字、命令、实验结果、具体例子。列不出几条，就说明还没到写的时候——这时候动笔，写出来的只能是形容词和自造词。

单子够了，句子会自己长出来，你只需要把单子上的东西连起来。跳过这一步直接写开头，就会开始找词填空。

## 技术文档里的落点

方案调研、技术验证、接口文档，落点各不相同。写之前先看清这次是哪一种。

| 写什么 | 落点是什么 | 最容易空转的地方 |
| --- | --- | --- |
| 方案调研 | 同一组指标下各方案的实测数字；版本、许可、成本；不选某条路的具体原因 | “性能更好”“生态完善” |
| 技术验证 | 环境与版本、操作步骤、原始输出、判定标准；失败的那几次 | “验证通过”“功能正常” |
| 接口文档 | 能直接复制的请求、真实返回、参数默认值与必填、错误码表 | “返回相应的错误” |

调研的结论要能被反驳：写清按哪个指标选的、放弃了什么。只写“综合来看 A 更合适”，读者既判断不了，也反驳不了。

接口文档的示例要能直接粘进终端跑，返回贴真实抓到的。手写一个“理想返回”，读者照着调不通。

## 形容词要有数字

技术文档里空转得最多的不是名词，是形容词：高效、稳定、灵活、强大、完善、优异、无缝、显著、大幅。它们没有落点，只能让读者自己想象。

| 空话 | 换成 |
| --- | --- |
| 性能优异 | 4 路并发下 p99 为 38ms；同机、同数据集，B 方案 120ms |
| 毫秒级推流、秒级响应 | 500ms 批处理窗口合并推送；查询 p95 ≤ 1000ms（没测过就写“实时推流”） |
| 生态完善 | 官方 SDK 两个；最近一次发布 2026-09 |
| 兼容性好 | 兼容 v2.1 到 v2.6；v3.0 起移除 XML 支持 |
| 支持高并发 | 单机 2000 QPS 时错误率 0.02% |
| 验证通过 | 连续跑 6 小时，RSS 稳定在 180MB±5MB，日志无 ERROR |

换不出数字，说明还没测。要么去测，要么把这句删掉。

数字要带条件。同一个数字，换了机器、版本、数据集就不是一回事；缺条件的数字比没有数字更糟，读者会拿它去比。

## 数据大于解释

**先摆数据，再给解释；解释不能替数据上场。**

「形容词要有数字」管的是词：把“优异”换成数字。这节管的是顺序——一段话里“表明”“说明”后面的解释都在，它指的那次实验、那个数字却不在，解释把数据的位置占了。

| 写法 | 改法 |
| --- | --- |
| 压测表明系统在高并发下表现稳定 | 2000 QPS 跑 30 分钟，错误率 0.02%，无超时 |
| 从内存曲线可以看出存在泄漏 | 6 小时 RSS 从 120MB 涨到 1.8GB，重启回落——是泄漏 |
| 综合来看 A 更适合我们 | 选 A：p99 38ms 对 120ms，代价是月成本 ¥400 对 ¥300——我们保延迟 |
| 大量实验验证了优化的有效性 | 同机同数据集 5 次：改前均值 2.1s，改后 0.3s |

判别是机械的：全文搜“表明、说明、可见、意味着、反映、体现、证明、验证、显然”，每处命中往回看一句——它指的数字、那次输出在本文里吗？不在就补，补不出来就连解释一起删。“测试表明一切正常”一个字都没说。

结论仍在第一句，但结论后面跟数据，不跟另一句解释。“选 A”是结论，“38ms 对 120ms”是数据，“因为延迟是硬指标”是解释——解释可以省，数据不能。

## 起名字是要花钱的

名字只在**要反复引用**时才划算。全文只提一次的步骤，直接写动作：

- 写“交出去之前自己过一遍”，不写“门禁”。
- 写“把没用的删掉”，不写“密度裁剪”。
- 写“先查事实再动笔”，不写“取证式”。

怎么判断：这个词在文中出现第二次了吗？没有，就展开成动作。

## 省字省到读者要脑补，就过头了

落点管的是词里没东西；反过来的病是词都有东西，组织没了——主语、范围、条件全省，读者要自己往回填。

| 写法 | 读者要脑补的 |
| --- | --- |
| spawn 期 malloc 非法访问 | 谁 spawn、malloc 访问了什么叫非法、发生在进程哪一端 |
| ARM64 不现 | 不复现什么、在什么条件下 |
| 堆锁损坏 | 堆的哪把锁、怎么个坏法 |

每句问一遍：第一次读的人要脑补什么？主语、宾语、范围、条件，补不回来的就写回去。

压缩造词是同源的病：private-network container 压成「私网容器」，re-register 压成「复注册」——每个字都有来处，组合没人认。它和「起名字」是同一条规则：起了没人认的名字。

## 句子

**长短不是标准，一句话里装了几个条件才是。**

样本《Super-agent 设计探索》10648 个汉字：平均 54.1 字一句，中位 47 字，最长 194 字，平均每句 2.29 个逗号。它不是短句文风。

> 「如果每条事件都交给同一个 Session 处理，虽然上下文最连续，但受限于单个 ReAct Loop 串行执行的速度上限，任务完成耗时长、吞吐低，且多任务的中间细节混杂在一起也会影响完成效果。」
>
> 「不需要介入时则保持安静。」

第一句四层条件，短了说不清。第二句一个判断，长了就散。节奏是长句铺陈述、短句收判断。

反过来，通篇短句的清单体读起来更差——它把该连起来说的话拆碎了。

长句成立有前提：每层条件删掉一层意思就缺、每个指代都指得清、从句不嵌套两层。绕弯的长句照样拆——拆不拆看绕不绕，不看长短。

## 简单明了

**第一遍读不回头，才算写明白了。**

「省字」一节管的是删过头：信息没了，读者要脑补。这节管的是反过来的病：信息都在，顺序不对——读者读着读着要往回翻。四条标准：

- **一句一个意思。** 一个判断可以叠条件、叠让步、叠同类事实，叠完还是一个意思，多长都留（见「句子」一节）。“另外”“同时”后面换个主语继续论证，是第二个判断，拆。判别：这句读完问“它下了几个判断”，答出两个就拆。
- **先结论后条件。** 条件堆在结论前，读者得背着条件等下半句。判断提前，条件用“前提是”“条件是”挂在后面。判别：删掉条件主句还成立（只是范围变大），是限制条件，后置；删掉条件主句就没了，是推导前提——“因为……所以……”的顺序不动，前提本身就是内容。
- **段首给判断。** 每段第一句是这段自己的结论——“结论放第一句”从句子推广到段落。判别：把各段首句抽出来连读，读得出全文骨架就合格；首句是“接下来介绍”“下面分析”的，判断没到场，换掉。
- **段间看得出关系。** 并列、递进还是转折，写出来，不靠读者猜。判别：指着每段首句问“它和上一段什么关系”，答不出，就补一个实义连接词（因此、反过来、相比之下）或者重排——空转的“综上所述”照旧删。

和「句子」一节是一件事的两面：它管“别因为长就拆”，这里管“别因为短就放过”——四层条件服务一个判断照样留，两个判断挤进一个短句照样拆。

## 直接写含义、范围和计算方式

技术说明中，按实际含义把“口径”展开成“含义”“统计范围”“计算方式”“数据来源”，或在非统计场景下展开成“状态定义”“取值规则”“去重规则”“判定条件”。选择能回答读者问题的词。

| 原写法 | 改法 |
| --- | --- |
| 实现及口径 | 含义与计算方式 |
| 字段单位及口径 | 字段单位和计算方式 |
| 未确认口径的字段 | 尚未确认含义和数据来源的字段 |
| 内存统计口径 | 内存统计范围 |
| 两个接口口径一致 | 两个接口采用相同的计算方式 |
| 状态口径 | 状态定义 |
| 一次连接一条记录的去重口径 | 一次连接一条记录的去重规则 |
| 0 表示永久保留的口径 | 0 表示永久保留的规则 |
| 跨文档口径 | 跨文档定义与状态 |

写完搜索“口径”，按上下文逐处替换。引用原文、正式名称或孔径等具体含义保留原词。

## 直接说明行为，限制集中写

先写实现做了什么，再写影响使用的条件。连续的“不代表……也不代表……”“不用……代替……也不把……”容易把技术说明写成免责声明。

| 原写法 | 改法 |
| --- | --- |
| 换算成纳秒不代表具备纳秒测量精度 | 单位为纳秒，精度为系统 tick |
| 不用零值代替失败结果，也不把旧数据标成新时间 | 采样失败时接口返回不可用错误，等待下一轮成功采样 |
| 这个 0 不代表容器没有使用内存 | 这里的 0 表示内存计数不可用 |

同一限制集中说明一次，写清触发条件和具体影响。涉及数据丢失、误差和使用前提的事实应保留；需要明确禁止的操作仍直接写“禁止”。

## 理性，不要感叹

**强调靠数字和位置，不靠符号。**

感叹号、emoji、程度词是同一样东西：作者想强调，手里又没有比“很”更具体的，只好加符号。技术写作里情绪是冗余信息——读者要的是那个数字，不是作者有多激动。判断放在句首、数据摆在那里，本身就是强调。

| 写法 | 换成 |
| --- | --- |
| 🚀 颠覆性重构调度器，性能碾压旧版！ | 重构调度器：8 核吞吐 1.2 万 → 1.7 万 QPS |
| 修复了一个极其严重的 bug！！！ | 修复 X 条件下的写丢失 |
| 性能提升非常显著！直接起飞🔥 | p99 从 120ms 降到 38ms |
| 震惊！一行配置搞垮整个集群 | 一次配置回退导致的集群不可用 |
| 新功能简直太强大了，强烈推荐！ | 支持 X、Y；不支持 Z |
| 新版重磅来袭，体验直接拉满💥 | v2.3 发布：新增 A，修复 B |
| 军工级稳定、企业级性能、电影级体验 | 过去 12 个月可用性 99.99%，两次故障共 43 分钟 |

判别是机械的，可以直接交给脚本跑：

- 连续标点：`rg '[!！?？]{2,}'`。单独的 `！` `!` 也搜一遍——技术文档里它合理出现的次数接近零，每一处都要说出理由。
- emoji：`rg '[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]'`；提交信息同样搜：`git log --oneline | rg '[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]'`
- 夸张词：`rg '非常|极其|颠覆|碾压|秒杀|震惊|炸裂|爆表|天花板|重磅|史诗|无敌|神器|拉满|简直|起飞'`
- “XX 级”式夸大与伪量化：`rg '(企业|工业|军工|旗舰|电影|殿堂|史诗|世界|顶尖|顶级|国民|银行|毫?秒|分钟|百|千|万|亿)级'`——拿名词当形容词夸品质，或者挂个时间/数量单位充当实测数据，换成具体数字或删掉。命中先看是不是真实分级：风险等级、保密级别、API 级别、进程级、连接级、行级、包级、文件级、字段级、报文级是分类或粒度，不动。

命中不一定是病：“秒杀”可能是功能名，报错输出里的 `!` 是真实输出不是文风——看一眼再动。其余的，程度词能换数字就换数字，换不了就删，句子通常还在。

## 写完自查

判别比生成容易。写的时候不知道自己在造词，写完一查就露。所以不靠感觉，靠查。

### 一、圈出抽象名词，问它指什么

把稿子里的抽象名词圈出来：机制、体系、维度、层面、路径、能力、闭环、赋能、抓手、门禁……逐个问一句：本文哪一句给了它落点？

指不到具体东西的，只有两条路——删掉，或者换成它本来指的那件事。

### 二、搜自己新造的词

冒出“两个抽象名词拼起来”的新词，直接搜：这个词在别人的中文里出现过吗？「结构自咬合」一条命中都没有，「存算分离」在华为云、StarRocks、腾讯云的正式文档里都有——自己编的词在真实语料里搜不到，真词不会。

### 三、别按字频改稿

同一篇好文章，和一份全是大词的稿子并排比：

| 指标 | 好文章 | 大词稿 |
| --- | --- | --- |
| 平均句长 | 54.1 字 | 23.4 字 |
| 每句逗号 | 2.29 个 | 0.94 个 |
| 虚动词（进行、实现、使得）每千字 | 2.2 个 | 0 个 |
| 连接词每千字 | 1.7 个 | 0 个 |
| 抽象大词每千字 | 1.5 个 | 0 个 |

每一项都是大词稿更“干净”。它是清单体：句子短、没有连接词、没有抽象名词，形式上一点都不像译文。但每个词都是编的，读完什么都没剩下。

好文章是论述体：句子长，有“因此”，有抽象名词，形式上更像翻译。但每个词背后都有东西——一次调用、一个数字、一段代码。

所以字频只能看出体裁写错了，看不出有没有内容。译文腔不在字频里，在落点里。

### 四、扫一遍生硬词

按「翻译腔」一节的「生硬」档和「没翻」档词表全文搜：生硬的换日常说法，没翻的翻成中文。再扫一遍有没有英文单词散在中文句子里（代码标识符和程序输出不算）。

这一步是机械的，可以直接交给脚本跑。但要看方向：把「缺页」改成「页面错误」就是改反了。

### 五、同一概念，全文一个说法

把稿子里的术语逐个搜一遍：`handle`/`句柄`、`半建`/`半创建` 这类一个概念两种写法，统一成一个。规范定死的词表（必现/偶现/待确认）反向也成立——它们是枚举值不是文风，只能往规范词收敛。

### 六、逐句过电报体

第一次读的人要脑补什么，逐句问一遍（见「省字省到读者要脑补」一节）。

### 七、扫一遍感叹号和表情

全文搜感叹号、连续标点、emoji、程度词和“XX 级”式夸大——词表和命令在「理性，不要感叹」一节。命中：能换数字换数字，换不了就删。引用原文和真实输出不动。

### 八、改存量文档时的保护边界与一键自查

改仓库已有文档时，先排除三类不能直接改写的位置：

- **标题锚点引用**：改标题里的“门禁 / 契约 / 口径”前，先搜 `rg '\]\([^)]*#'`，把指向旧标题锚点的链接一并更新。
- **原始取证文件**：客户需求原件（如 `.project/`）、外部协议原文、终端原始输出，保持原样。
- **规则中的反例表**：规范文档里列举“禁止使用：赋能、秒级、多维度”的词表，是反例，不删。

动完笔直接跑一遍组合扫描：

```bash
# 1. 口径与生硬词
rg '口径|门禁|契约|可交付|坐实|抓手|赋能|闭环|物理上|一侧'
# 2. 解释压过数据（逐处往回看一句有没有数字或输出）
rg '表明|说明|可见|意味着|反映|体现|证明|验证|显然'
# 3. 抽象空转与冗余名词化
rg '维度|层面|机制|体系|进行[^行中]|在.*方面|对于.*而言|就.*而言|综上所述|值得注意的是'
# 4. 感叹号、emoji、夸张词与伪量化
rg '[!！?？]{2,}|[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]|非常|极其|颠覆|碾压|秒杀|震惊|炸裂|爆表|天花板|重磅|史诗|无敌|神器|拉满|简直|起飞|(企业|工业|军工|旗舰|电影|殿堂|史诗|世界|顶尖|顶级|国民|银行|毫?秒)级'
# 5. 散落在中文句子里的未加反引号英文词
rg '[^`'"'"'"/a-zA-Z0-9_-](stale|no-op|race|side|deliverable|freshness|spec|reviewable|fallback)[^`'"'"'"a-zA-Z0-9_-]'
```

## 翻译腔：用国内同行的说法

判断一个词该不该用，只问一句：**国内做这行的工程师，会不会这么说？**

不是问它从哪来。冒烟、回归、缺页、死锁、竞态条件、脏页、灰度、回滚、幂等——全是从英文翻的，但中文技术文档里到处都是，用过的人一眼就懂。反过来，门禁、契约、可交付、坐实——词是中文，组合不是，读着别扭。

| 档 | 怎么认 | 例子 | 怎么办 |
| --- | --- | --- | --- |
| 通行 | 中文技术文档里搜得到 | 冒烟测试、回归、缺页、脏页、竞态条件、灰度、回滚、幂等、熔断 | 直接用，别另翻 |
| 生硬 | 中文里没人这么组合 | 门禁、契约、可交付、坐实、抓手、赋能、闭环、物理上、一侧、筛选维度、分层维度 | 换成日常说法 |
| 没翻 | 英文单词散在中文句子里 | stale、no-op、race、side、deliverable、freshness、spec、reviewable | 翻成中文，或给代码字段加反引号 |

拿不准就搜：中文技术文档里一条命中都没有，就是生硬。

### 换法

| 生硬 | 换成 |
| --- | --- |
| 交付前门禁 | 交出去之前自己过一遍 |
| 接口契约 | 接口约定、接口文档 |
| 可交付的方案 | 能用的改法 |
| 坐实了机制 | 证明是这个原因 |
| 物理上是两张表 | 本来就是两张表 |
| 消掉竞态的一侧 | 把其中 unmap 这一步去掉 |
| 静默 no-op | 返回成功、实际不执行 |
| 筛选维度、分层维度、日期主维度 | 筛选条件、分类、主日期字段 |
| 台账 spec、复制 freshness 条件、reviewable 文件 | 台账规格、重复实现在线窗口判定条件、待审文件 |

注意「竞态」本身是通行词（内核文档、面试题都在用），生硬的是「竞态的一侧」——把英文 side 直译进了中文。问题常在搭配，不总在单词。

### 别改过头

标准是“同行说不说”，不是“是不是翻译”。换过头比不换更糟：

- 根因、静默失败、样本、缓解、反模式——运维和内核文档里都在用，保留。
- 缺页、死锁、脏页、回滚、灰度、冒烟——通行说法，别改成“页面错误”“页面脏”。

统一近义词之前先问有没有分工：「挂死」（等锁死）和「卡死」（空转卡）是 hung 和 stuck 两种死法，拉平成一个词就丢一层信息；规范枚举值（必现/偶现/待确认）是取值表不是文风，更不能动。

验证不靠人肉通读：改前搜语料确认通行，改后全文 grep——替换词没有漏网，也没误伤同形词（「假死」不是「卡死」，「半创建」里有「半建」）。

### 句子层面的翻译腔

词对了，句子骨架还可能是英文的。四种常见：

- **介词短语前置**：「在……方面」「对于……而言」「就……而言」。删掉，直接说谁做了什么。
- **被动**：「被认为」「被广泛使用」。中文更常说「大家认为」「普遍用」。
- **名词化**：「进行处理」「进行优化」「做出确认」。直接说「处理」「优化」「确认」。
- **判断藏在后半句**：「这意味着……」「由此可以看出……」。把判断提到句首。

改法不是换同义词，是把句子重写成中文的说法：删掉介词短语，把名词拆回动作，句子通常就顺了。

翻译腔和造词不是一回事：造词是编一个中文里没有的组合（交付前门禁），翻译腔是照英文的骨架组词（物理上是两张表）。两者都“读着不像中文”，但改法不同——造词要删，翻译腔要换一种说法。

代码里的标识符（函数名、变量名、宏名）保持原样，不翻译。

## 常见写法对照

| 症状 | 长什么样 | 怎么改 |
| --- | --- | --- |
| 名词化 | 实现了向更高层决策与验收的上移 | 上移到更高层的决策与验收 |
| 万能动词 | 对上下文注入进行优化 | 少注入，需要时再取 |
| 空转连接词 | 综上所述、值得注意的是 | 删；实义的“因此”“反过来”可以留 |
| 判断藏在句尾 | 经过分析，我们认为…… | 结论放第一句 |
| 自证式 | 我试了 A，又试了 B，最后发现…… | 已验证：A 可行；B 失败，原因是…… |
| 排比凑数 | 不仅……而且…… | 一条说清，剩下的删 |
| 模糊限定 | 通常会……、一般是…… | 补条件，或者标出处 |
| 术语倒装 | Speculative Execution | 投机执行（Speculative Execution） |
| 符号强调 | 性能炸裂！性能炸裂！🚀 | p99 38ms，改前 120ms |
| 解释压过数据 | 压测表明系统表现稳定 | 2000 QPS 跑 30 分钟，错误率 0.02% |

中文在前，英文在括号里。反过来是译文腔；自己生造中文译名是另一种毛病，读者查不到，也记不住。

## 什么时候别用这套

- 宣传稿、对外文案：要短、要响，这套规则会让它变平。
- 创意写作：节奏本身就是内容。
- 术语已有公认中文名的，用中文名，不要另起一个。
- 取证笔记、排障日志、实验记录：简略半角是体裁不是毛病。同一仓库可以有多个语域，仓库规范（AGENTS.md 类）另有约定时以规范为准。

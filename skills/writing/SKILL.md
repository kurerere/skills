# 写中文：先有落点，再写句子

这套规则只管语言与事实表达，不管宏观排版布局，不依赖其他技能。写文档时使用。

## 一条主规则

**先有落点，再写句子。**

落点是这句话能指到的具体东西：数字、命令、实验结果、代码、真实 Trace ID / 时序图、具体的人或物。

动笔之前手里没有落点，句子就会自己去找替代品。最顺手的替代品，是把两个抽象名词拼成一个新词。黑话不是文风问题，是没东西可写的时候用来填空的。

| 本来要说的 | 造出来的词 | 问题 |
| --- | --- | --- |
| 交出去之前自己对照清单过一遍 | 交付前门禁 | 把人工自查拔高成系统机制 |
| 判断哪些该留、哪些该删 | 密度裁剪 | “密度”“裁剪”都是比喻，没有落点 |
| 说清为什么不选另一条路 | 成对取舍 | 同上 |
| 底层实际分成两张表存 | 物理上是两张表 | 拿英文 physical 直译凑词 |

这四个词拿去搜，一条命中都没有。真词不会这样。

## 动笔之前，先把落点列出来

写之前列一张单子：这次要用的指标数字、命令、Trace、实验输出、具体例子。列不出几条，说明还没测或者事实还没拿到——这时候动笔，写出来的只能是形容词和自造词。

单子够了，句子会自己长出来，你只需要把单子上的东西连起来。跳过这一步直接写开头，就会开始找词填空。

## 技术文档里的落点（按场景抓事实）

方案调研、技术验证、接口文档、故障复盘、架构设计，落点各不相同。写之前看清这次是哪一种，把必备的落点要素找齐：

| 写什么 | 落点是什么（必备事实清单） | 最容易空转的套话 |
| --- | --- | --- |
| 方案调研 | 同一组指标下各方案的实测数字；版本、许可、成本；不选某条路的具体致命缺陷 | “性能更好”“生态完善” |
| 技术验证 | 环境与版本、操作步骤、原始输出、判定标准；失败的那几次与边界表现 | “验证通过”“功能正常” |
| 接口文档 | 能直接跑的完整 cURL、带字段约束的真实返回、参数必填与默认值、错误码表 | “返回相应的错误” |
| 故障复盘 | 分钟级时间线（Timeline）、受影响面（报错量/用户数）、根因、带责任人与日期的 Action Items | “加强防范意识”“做好代码检查” |
| 架构设计 / RFC | Non-Goals（坚决不做的范围）、峰值 QPS 与容量测算、下游故障时的降级表现 | “高可用高并发架构”“灵活扩展” |

- **调研的结论要能被反驳**：写清按哪个指标选的、放弃了什么。只写“综合来看 A 更合适”，读者既判断不了，也反驳不了。
- **接口文档示例要能直接跑**：示例粘进终端就能执行，返回贴真实抓到的。手写一个“理想返回”，读者照着调不通。
- **复盘改进项只写真实工程动作**：不写口号，写“加监控报警阈值”、“流水线接入自动化拦截”，且每项必须有人名和截止日期。

## 形容词要有数字与工件

技术文档里空转得最多的不是名词，是形容词：高效、稳定、灵活、强大、完善、优异、无缝、显著、大幅。它们没有落点，只能让读者自己想象。

| 空话 | 换成落点（数字、条件与工件） |
| --- | --- |
| 性能优异 | 4 路并发下 p99 为 38 ms；同机、同数据集，B 方案 120 ms |
| 毫秒级推流、秒级响应 | 500 ms 批处理窗口合并推送；查询 p95 ≤ 1000 ms（没测过就写“实时推流”） |
| 生态完善 | 官方 SDK 两个；最近一次发布 2026-09 |
| 兼容性好 | 兼容 v2.1 到 v2.6；v3.0 起移除 XML 支持 |
| 支持高并发 | 单机 2000 QPS 时错误率 0.02% |
| 链路可追踪 | 关键入口注入 Trace ID，通过 Jaeger 查询 span: `order.checkout` |
| 验证通过 | 连续跑 6 小时，RSS 稳定在 180 MB ± 5 MB，日志无 ERROR |

换不出数字或证据，说明还没测。要么去测，要么把这句删掉。数字要带条件（机器、版本、并发量）。缺条件的数字比没有数字更糟，读者会拿它去比。

## 数据大于解释

**先摆数据，再给解释；解释不能替数据上场。**

一段话里“表明”“说明”后面的解释都在，它指的那次实验、那个数字却不在，解释把数据的位置占了。

| 写法 | 改法 |
| --- | --- |
| 压测表明系统在高并发下表现稳定 | 2000 QPS 跑 30 分钟，错误率 0.02%，无超时 |
| 从内存曲线可以看出存在泄漏 | 6 小时 RSS 从 120 MB 涨到 1.8 GB，重启回落——是泄漏 |
| 综合来看 A 更适合我们 | 选 A：p99 38 ms 对 120 ms，代价是月成本 ¥400 对 ¥300——我们保延迟 |
| 大量实验验证了优化的有效性 | 同机同数据集 5 次：改前均值 2.1 s，改后 0.3 s |

判别是机械的：全文搜“表明、说明、可见、意味着、反映、体现、证明、验证、显然”，每处命中往回看一句——它指的数字、那次输出在本文里吗？不在就补，补不出来连解释一起删。“测试表明一切正常”一个字都没说。

结论仍在第一句，但结论后面跟数据，不跟另一句解释。“选 A”是结论，“38 ms 对 120 ms”是数据，“因为延迟是硬指标”是解释——解释可以省，数据不能。

## 大词与术语：白名单收敛与动词还原

大词容易变成 AI 用来掩盖细节的捷径。对于“门禁、契约、物理、降级”等词，执行**默认禁用，仅在固定专有名词白名单中放行**：

| 词汇 | 允许的白名单（固定专有名词） | 禁用的滥用场景（必须动词还原） |
| --- | --- | --- |
| **门禁** | `代码门禁`、`CI 门禁`、`发布门禁`（专指自动化流水线拦截工具） | 不写：交付前门禁、逻辑门禁 → 写：**交出去前对照清单自查**、**参数前置校验** |
| **契约** | `契约测试`、`Pact 契约`（专指 Contract Testing 自动化测试体系） | 不写：接口契约、通信契约 → 写：**双方约定的返回字段**、**接口协议规范** |
| **物理** | `物理表`、`物理库`、`物理分片`、`物理拓扑`（专指分库分表与硬件拓扑） | 不写：物理上是两张表 → 写：**底层实际存储为两张表** |
| **降级/熔断** | `熔断降级`（专指微服务分布式容灾策略） | 不写：对异常进行了降级处理 → 写：**网络超时返回默认空列表** |

**动词还原法则**：凡不在白名单内的抽象名词，强迫拆成 **【主语】在【阶段】做了什么【动作】**。
- 写“交出去之前自己过一遍”，不写“门禁”。
- 写“把没用的删掉”，不写“密度裁剪”。
- 写“先查事实再动笔”，不写“取证式”。

起名字是要花钱的。名字只在**要反复引用**时才划算。全文只提一次的步骤，直接写动作。

## 拒绝 AI 结构八股

除了句子层面的语言，消除以下 3 种典型的 AI 结构特征：

1. **删掉结尾废话与免责总结**：严禁出现“综上所述，具体方案需结合业务场景实际权衡选择”这类无信息增量的空话。核心结论放第一段，正文讲完即止。
2. **禁止虚假的对称清单**：对比方案时，严禁为了形式美观硬凑“3 优 3 缺”。必须写出当前业务权衡的核心权重，以及被否决方案的具体致命短板。
3. **删掉章节前铺垫套话**：删掉“在深入探讨 X 之前，我们首先来看看……”等套话过渡，直接陈述正文。

## 中文技术排版规范

国内规范技术文档（开源规范、云厂商手册）对排版有确定要求，格式糙会直接破坏严肃性：

1. **盘古之白（中英间隔）**：汉字与英文字符、数字之间保留 1 个半角空格。
   - 不写：`使用Redis作为缓存，提升QPS到2000`
   - 写：`使用 Redis 作为缓存，提升 QPS 到 2000`
2. **专有名词大小写严格遵循官方规范**：
   - 严禁随意全小写或全大写。
   - 常见标准写法：`PostgreSQL`、`GitHub`、`Kubernetes`、`Nginx`、`Redis`、`MySQL`、`Spring Boot`、`Vue`、`iOS`。
3. **量词与单位**：数值与英文单位之间保留 1 个空格（`38 ms`、`2000 QPS`、`180 MB`；百分比 `%` 与度数 `°` 紧贴数字，不留空格）。

## 省字省到读者要脑补，就过头了

落点管的是词里没东西；反过来的病是词都有东西，组织没了——主语、范围、条件全省的“电报体”，读者要自己往回填。

| 写法 | 读者要脑补的 | 改写 |
| --- | --- | --- |
| spawn 期 malloc 非法访问 | 谁 spawn、malloc 访问了什么叫非法、发生在进程哪一端 | 子进程在 spawn 初始化阶段调用 malloc 越界 |
| ARM64 不现 | 不复现什么、在什么条件下 | 该问题在 ARM64 架构下未复现 |
| 堆锁损坏 | 堆的哪把锁、怎么个坏法 | 堆分配器的全局互斥锁状态被异常覆写 |

每句问一遍：第一次读的人要脑补什么？主语、宾语、范围、条件，补不回来的就写回去。
压缩造词也是同源病：private-network container 压成「私网容器」，re-register 压成「复注册」——每个字都有来处，组合没人认。

## 句子与节奏

**长短不是标准，一句话里装了几个条件才是。**

长句铺陈述、短句收判断。通篇短句的清单体读起来更差——它把该连起来说的话拆碎了。

- **一句一个意思**：一个判断可以叠条件，叠完还是一个意思，多长都留。“另外”“同时”后面换个主语继续论证，是第二个判断，拆。
- **先结论后条件**：条件堆在结论前，读者得背着条件等下半句。限制条件后置，推导前提保留因果顺序。
- **段首给判断**：每段第一句是这段自己的结论。把各段首句抽出来连读，读得出全文骨架就合格；首句是“接下来介绍”“下面分析”的，换掉。
- **段间看得出关系**：并列、递进还是转折，用实义连接词（因此、反过来、相比之下）写出来，空转的“综上所述”照旧删。

## 翻译腔：用国内同行的说法

判断一个词该不该用，只问一句：**国内做这行的工程师，会不会这么说？**

| 档 | 怎么认 | 例子 | 怎么办 |
| --- | --- | --- | --- |
| 通行 | 中文技术文档里搜得到 | 冒烟测试、回归、缺页、脏页、竞态条件、灰度、回滚、幂等、熔断 | 直接用，别另翻 |
| 生硬 | 行业通用性低或概念拔高 | 可交付、坐实、抓手、赋能、闭环、一侧、筛选维度 | 换成日常说法或具体动作 |
| 没翻 | 英文单词散在中文句子里 | stale、no-op、race、side、deliverable、freshness、spec | 翻成中文，或给代码字段加反引号 |

- 常见改法：`可交付的方案` → `能用的改法`；`坐实了机制` → `证明是这个原因`；`静默 no-op` → `返回成功、实际不执行`；`筛选维度` → `筛选条件`。
- 竞态本身是通行词，生硬的是“消掉竞态的一侧”——把英文 side 直译进了中文。问题常在搭配，不总在单词。
- 句子层面的翻译腔：
  - **介词短语前置**（在……方面/对于……而言） → 删掉，直奔主谓宾。
  - **被动**（被认为/被广泛使用） → 中文更常说“普遍用”“通常选”。
  - **万能动词**（进行优化/做出确认） → 直接说“优化”“确认”。
  - **判断藏在后半句**（这意味着……） → 结论提到句首。

## 直接写含义、范围和计算方式

技术说明中，按实际含义把“口径”展开成“含义”“统计范围”“计算方式”“数据来源”，或在非统计场景下展开成“状态定义”“取值规则”“去重规则”“判定条件”。选择能回答读者问题的词。

| 原写法 | 改法 |
| --- | --- |
| 实现及口径 | 含义与计算方式 |
| 字段单位及口径 | 字段单位和计算方式 |
| 内存统计口径 | 内存统计范围 |
| 两个接口口径一致 | 两个接口采用相同的计算方式 |
| 状态口径 | 状态定义 |

先写实现做了什么，再集中写影响使用的限制。同一限制集中说明一次，写清触发条件和具体影响。

## 理性，不要感叹

**强调靠数字和位置，不靠符号与夸张词。**

技术写作里情绪是冗余信息——读者要的是数字和边界，不是作者有多激动。判断放在句首、数据摆在那里，本身就是强调。

- 连续标点与感叹号：技术文档里合理出现的感叹号接近零。
- emoji：技术文档与代码提交信息中严禁夹带。
- 夸大词与伪量化：删掉“颠覆/秒杀/炸裂/起飞/拉满”，换成真实性能指标；删掉“军工级/企业级/秒级”，换成真实可用性统计或具体时延数字。

## 写完自查与机械判别

判别比生成容易。写完不靠感觉，直接跑一遍扫描：

```bash
bash <SKILL_DIR>/scripts/check.sh <文件或目录>
```

脚本按六类扫描：口径与大词、门禁与契约、解释压过数据、空转过渡、感叹号与夸张词、专有名词大小写。`<SKILL_DIR>` 为本文件所在目录。命中后按下面的口诀逐处判断。

### 弱模型二值判别口诀

- **搜到「门禁」**：前面带 `CI`、`代码` 或 `发布`？ → 是：保留；否：展开为具体动作（跑检查/人工核对）。
- **搜到「契约」**：后面带 `测试`？ → 是：保留；否：换成 `约定`、`规范` 或 `定义`。
- **搜到「物理」**：后面带 `表`、`库`、`分片` 或 `拓扑`？ → 是：保留；否：换成 `底层`、`实际`。
- **搜到「综上所述 / 结合实际业务」**：整句直接删除。
- **检查英文混排**：英文与汉字之间是否都留了半角空格。

## 什么时候别用这套

- 宣传稿、对外文案：要短、要响，这套规则会让它变平。
- 创意写作：节奏本身就是内容。
- 术语已有公认中文名的，用中文名，不要另起一个。
- 取证笔记、排障日志、实验记录：简略半角是体裁不是毛病。同一仓库可以有多个语域，仓库规范（AGENTS.md 类）另有约定时以规范为准。

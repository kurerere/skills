# 写中文：先有落点，再写句子

这套规则只管语言，不管文档结构。结构（取证、排序、删减）见 `evidence-first-docs`。

对聊天回复同样适用——黑话大多出现在对话里，不在文档里。

## 一条主规则

**先有落点，再写句子。**

落点是这句话能指到的东西：一个数字、一条命令、一次实验、一段代码、一个具体的人或物。

动笔之前手里没有落点，句子就会自己去找替代品。最顺手的替代品，是把两个抽象名词拼成一个新词。黑话不是文风问题，是没东西可写的时候用来填空的。

| 本来要说的 | 造出来的词 | 问题 |
| --- | --- | --- |
| 交出去之前自己过一遍 | 交付前门禁 | 中文里没有这个组合，读者得猜 |
| 判断哪些该留、哪些该删 | 密度裁剪 | “密度”“裁剪”都是比喻，落不到具体的东西上 |
| 说清为什么不选另一条路 | 成对取舍 | 同上 |
| 图和章节对得上 | 结构自咬合 | 借了牙科的词 |

这四个词拿去搜，一条命中都没有。真词不会这样。

## 动笔之前，先把落点列出来

写之前列一张单子：这次要用的数字、命令、实验结果、具体例子。列不出几条，就说明还没到写的时候——这时候动笔，写出来的只能是形容词和自造词。

单子够了，句子会自己长出来，你只需要把单子上的东西连起来。跳过这一步直接写开头，就会开始找词填空。

## 技术文档里的落点

方案调研、技术验证、接口文档，落点各不相同。写之前先看清这次是哪一种。

| 写什么 | 落点是什么 | 最容易空转的地方 |
| --- | --- | --- |
| 方案调研 | 同一组指标下各方案的实测数字；版本、许可、成本；不选某条路的具体原因 | “性能更好”“生态完善” |
| 技术验证 | 环境与版本、操作步骤、原始输出、判定标准；失败的那几次 | “验证通过”“功能正常” |
| 接口文档 | 能直接复制的请求、真实返回、参数默认值与必填、错误码表 | “返回相应的错误” |

调研的结论要能被反驳：写清按哪个指标选的、放弃了什么。只写“综合来看 A 更合适”，读者既判断不了，也反驳不了。

接口文档的示例要能直接粘进终端跑，返回贴真实抓到的。手写一个“理想返回”，读者照着调不通。

## 形容词要有数字

技术文档里空转得最多的不是名词，是形容词：高效、稳定、灵活、强大、完善、优异、无缝、显著、大幅。它们没有落点，只能让读者自己想象。

| 空话 | 换成 |
| --- | --- |
| 性能优异 | 4 路并发下 p99 为 38ms；同机、同数据集，B 方案 120ms |
| 生态完善 | 官方 SDK 两个；最近一次发布 2026-09 |
| 兼容性好 | 兼容 v2.1 到 v2.6；v3.0 起移除 XML 支持 |
| 支持高并发 | 单机 2000 QPS 时错误率 0.02% |
| 验证通过 | 连续跑 6 小时，RSS 稳定在 180MB±5MB，日志无 ERROR |

换不出数字，说明还没测。要么去测，要么把这句删掉。

数字要带条件。同一个数字，换了机器、版本、数据集就不是一回事；缺条件的数字比没有数字更糟，读者会拿它去比。

## 起名字是要花钱的

名字只在**要反复引用**时才划算。全文只提一次的步骤，直接写动作：

- 写“交出去之前自己过一遍”，不写“门禁”。
- 写“把没用的删掉”，不写“密度裁剪”。
- 写“先查事实再动笔”，不写“取证式”。

怎么判断：这个词在文中出现第二次了吗？没有，就展开成动作。

## 省字省到读者要脑补，就过头了

落点管的是词里没东西；反过来的病是词都有东西，组织没了——主语、范围、条件全省，读者要自己往回填。

| 写法 | 读者要脑补的 |
| --- | --- |
| spawn 期 malloc 非法访问 | 谁 spawn、malloc 访问了什么叫非法、发生在进程哪一端 |
| ARM64 不现 | 不复现什么、在什么条件下 |
| 堆锁损坏 | 堆的哪把锁、怎么个坏法 |

每句问一遍：第一次读的人要脑补什么？主语、宾语、范围、条件，补不回来的就写回去。

压缩造词是同源的病：private-network container 压成「私网容器」，re-register 压成「复注册」——每个字都有来处，组合没人认。它和「起名字」是同一条规则：起了没人认的名字。

## 句子

**长短不是标准，一句话里装了几个条件才是。**

样本《Super-agent 设计探索》10648 个汉字：平均 54.1 字一句，中位 47 字，最长 194 字，平均每句 2.29 个逗号。它不是短句文风。

> 「如果每条事件都交给同一个 Session 处理，虽然上下文最连续，但受限于单个 ReAct Loop 串行执行的速度上限，任务完成耗时长、吞吐低，且多任务的中间细节混杂在一起也会影响完成效果。」
>
> 「不需要介入时则保持安静。」

第一句四层条件，短了说不清。第二句一个判断，长了就散。节奏是长句铺陈述、短句收判断。

反过来，通篇短句的清单体读起来更差——它把该连起来说的话拆碎了。

## 写完自查

判别比生成容易。写的时候不知道自己在造词，写完一查就露。所以不靠感觉，靠查。

### 一、圈出抽象名词，问它指什么

把稿子里的抽象名词圈出来：机制、体系、维度、层面、路径、能力、闭环、赋能、抓手、门禁……逐个问一句：本文哪一句给了它落点？

指不到具体东西的，只有两条路——删掉，或者换成它本来指的那件事。

### 二、搜自己新造的词

冒出“两个抽象名词拼起来”的新词，直接搜：这个词在别人的中文里出现过吗？

| 词 | 搜索结果 |
| --- | --- |
| 结构自咬合 | 一条都没有 |
| 成对取舍 | 一条都没有 |
| 交付前门禁 | 一条都没有（“质量门禁”“安全门禁”有，但这是拼出来的组合） |
| 存算分离 | 大量命中，华为云、StarRocks、腾讯云的正式文档都在用 |

自己编的词在真实语料里一条都搜不到，真词不会。搜一次就知道。

### 三、别按字频改稿

同一篇好文章，和一份全是大词的稿子并排比：

| 指标 | 好文章 | 大词稿 |
| --- | --- | --- |
| 平均句长 | 54.1 字 | 23.4 字 |
| 每句逗号 | 2.29 个 | 0.94 个 |
| 虚动词（进行、实现、使得）每千字 | 2.2 个 | 0 个 |
| 连接词每千字 | 1.7 个 | 0 个 |
| 抽象大词每千字 | 1.5 个 | 0 个 |

每一项都是大词稿更“干净”。它是清单体：句子短、没有连接词、没有抽象名词，形式上一点都不像译文。但每个词都是编的，读完什么都没剩下。

好文章是论述体：句子长，有“因此”，有抽象名词，形式上更像翻译。但每个词背后都有东西——一次调用、一个数字、一段代码。

所以字频只能看出体裁写错了，看不出有没有内容。译文腔不在字频里，在落点里。

### 四、扫一遍生硬词

全文搜这几个词，命中就换：门禁、契约、可交付、坐实、抓手、赋能、闭环、物理上、一侧、静默、no-op、stale、race。

再扫一遍有没有英文单词散在中文句子里（代码标识符和程序输出不算）。

这一步是机械的，可以直接交给脚本跑。但要看方向：把「缺页」改成「页面错误」就是改反了。

### 五、同一概念，全文一个说法

把稿子里的术语逐个搜一遍：`handle`/`句柄`、`半建`/`半创建` 这类一个概念两种写法，统一成一个。规范定死的词表（必现/偶现/待确认）反向也成立——它们是枚举值不是文风，只能往规范词收敛。

### 六、逐句过电报体

第一次读的人要脑补什么，逐句问一遍（见「省字省到读者要脑补」一节）。

## 翻译腔：用国内同行的说法

判断一个词该不该用，只问一句：**国内做这行的工程师，会不会这么说？**

不是问它从哪来。冒烟、回归、缺页、死锁、竞态条件、脏页、灰度、回滚、幂等——全是从英文翻的，但中文技术文档里到处都是，用过的人一眼就懂。反过来，门禁、契约、可交付、坐实——词是中文，组合不是，读着别扭。

| 档 | 怎么认 | 例子 | 怎么办 |
| --- | --- | --- | --- |
| 通行 | 中文技术文档里搜得到 | 冒烟测试、回归、缺页、脏页、竞态条件、灰度、回滚、幂等、熔断 | 直接用，别另翻 |
| 生硬 | 中文里没人这么组合 | 门禁、契约、可交付、坐实、抓手、赋能、闭环、物理上、一侧 | 换成日常说法 |
| 没翻 | 英文单词散在中文句子里 | stale、no-op、race、side、deliverable | 翻成中文 |

拿不准就搜：中文技术文档里一条命中都没有，就是生硬。

### 换法

| 生硬 | 换成 |
| --- | --- |
| 交付前门禁 | 交出去之前自己过一遍 |
| 接口契约 | 接口约定、接口文档 |
| 可交付的方案 | 能用的改法 |
| 坐实了机制 | 证明是这个原因 |
| 物理上是两张表 | 本来就是两张表 |
| 消掉竞态的一侧 | 把其中 unmap 这一步去掉 |
| 静默 no-op | 返回成功、实际不执行 |

注意「竞态」本身是通行词（内核文档、面试题都在用），生硬的是「竞态的一侧」——把英文 side 直译进了中文。问题常在搭配，不总在单词。

### 别改过头

标准是“同行说不说”，不是“是不是翻译”。换过头比不换更糟：

- 根因、静默失败、样本、缓解、反模式——运维和内核文档里都在用，保留。
- 缺页、死锁、脏页、回滚、灰度、冒烟——通行说法，别改成“页面错误”“页面脏”。

统一近义词之前先问有没有分工：「挂死」（等锁死）和「卡死」（空转卡）是 hung 和 stuck 两种死法，拉平成一个词就丢一层信息；规范枚举值（必现/偶现/待确认）是取值表不是文风，更不能动。

验证不靠人肉通读：改前搜语料确认通行，改后全文 grep——替换词没有漏网，也没误伤同形词（「假死」不是「卡死」，「半创建」里有「半建」）。

### 句子层面的翻译腔

词对了，句子骨架还可能是英文的。四种常见：

- **介词短语前置**：「在……方面」「对于……而言」「就……而言」。删掉，直接说谁做了什么。
- **被动**：「被认为」「被广泛使用」。中文更常说「大家认为」「普遍用」。
- **名词化**：「进行处理」「进行优化」「做出确认」。直接说「处理」「优化」「确认」。
- **判断藏在后半句**：「这意味着……」「由此可以看出……」。把判断提到句首。

改法不是换同义词，是把句子重写成中文的说法：删掉介词短语，把名词拆回动作，句子通常就顺了。

翻译腔和造词不是一回事：造词是编一个中文里没有的组合（交付前门禁），翻译腔是照英文的骨架组词（物理上是两张表）。两者都“读着不像中文”，但改法不同——造词要删，翻译腔要换一种说法。

代码里的标识符（函数名、变量名、宏名）保持原样，不翻译。

## 常见写法对照

| 症状 | 长什么样 | 怎么改 |
| --- | --- | --- |
| 名词化 | 实现了向更高层决策与验收的上移 | 上移到更高层的决策与验收 |
| 万能动词 | 对上下文注入进行优化 | 少注入，需要时再取 |
| 空转连接词 | 综上所述、值得注意的是 | 删；实义的“因此”“反过来”可以留 |
| 判断藏在句尾 | 经过分析，我们认为…… | 结论放第一句 |
| 自证式 | 我试了 A，又试了 B，最后发现…… | 已验证：A 可行；B 失败，原因是…… |
| 排比凑数 | 不仅……而且…… | 一条说清，剩下的删 |
| 模糊限定 | 通常会……、一般是…… | 补条件，或者标出处 |
| 术语倒装 | Speculative Execution | 投机执行（Speculative Execution） |

中文在前，英文在括号里。反过来是译文腔；自己生造中文译名是另一种毛病，读者查不到，也记不住。

## 什么时候别用这套

- 宣传稿、对外文案：要短、要响，这套规则会让它变平。
- 创意写作：节奏本身就是内容。
- 术语已有公认中文名的，用中文名，不要另起一个。
- 取证笔记、排障日志、实验记录：简略半角是体裁不是毛病。同一仓库可以有多个语域，仓库规范（AGENTS.md 类）另有约定时以规范为准。

## 和其他技能的关系

- 写的是要读者照着做事的文档 → 结构用 `evidence-first-docs`，语言用这一份。
- 只是把现成的稿子去掉 AI 味 → `humanizer-zh` 或 `shuorenhua`，它们做编辑，不做生成。

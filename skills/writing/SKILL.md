# 写清楚，不改动事实

让读者第一次读就明白：说的是什么，为什么作出这个判断，适用于什么条件。语言服务于内容，不为符合固定句式牺牲准确性和阅读节奏。

## 必须守住的边界

- **润色不增加事实。** 不补出未经确认的原因、对象、范围或结果，不把可能、推断和局部观察改成确定结论。缺少信息时保留不确定性，或指出需要补充什么。
- **判断不能超过证据。** 数字带上影响理解的条件；观测、解释与结论分清。代码、配置、官方资料和用户明确给出的约束也可以是依据，不是每句话都需要实测数字。
- **不要删掉决定性的条件。** 简洁不能以读者猜主语、对象、触发条件或例外为代价。改写前后应保留相同的含义、承诺和限制。

例如：

| 已知信息 | 可以怎样写 | 不能凭空补出的结论 |
| --- | --- | --- |
| 6 小时 RSS 从 120 MB 增至 1.8 GB，重启后回落 | 保留观测；若原因未知，写明尚未确定 | 已证明存在内存泄漏 |
| malloc 调用期间发生非法访问 | 写清已知的调用场景，原因未定位就保留未知 | 已定位为缓冲区越界 |
| 请求在指定环境下 p99 为 38 ms | 同时给出版本、负载等必要条件 | 在其他环境也有相同时延 |

## 让表达有落点

先找到要传达的事实、决定或问题，再组织句子。用具体动作、行为、条件和例子替代没有内容的评价；“性能好”可以展开为测量结果，“兼容”可以展开为支持范围。没有证据时如实说明，不靠形容词填空。

沿用项目与行业术语。术语是否准确取决于上下文，不靠固定白名单裁决；“物理内存”“物理地址”等表达不能机械替换成“底层”或“实际”。词语让读者难懂时，解释它指的具体对象或动作。代码标识、协议名和必要的英文保留原文。

重要判断尽早给出，并在合适位置交代依据与取舍。因果解释、必要背景和适用限制有助于理解时保留。不要为了“先结论”打断必须先交代的条件，也不用让每段都套同一种开头。

删掉无信息增量的过渡、宣传式评价、重复总结和自造缩略词。不为形式凑对称列表，不把连续论述拆成碎句。篇幅、长短句、列表和段落按内容选择。

## 排版与自查

沿用项目文风；没有特别约定时，中英文和数字之间留适当空格，专有名词大小写与单位写法保持一致。不要为排版修改代码、路径、链接目标或原始输出。

交付前对照原始材料，重点看是否改动了含义、夸大了结论、漏掉了条件，以及读者是否还需要回头猜句意。

需要辅助检查时，可运行：

```bash
bash <SKILL_DIR>/scripts/check.sh <文件或目录>
```

`<SKILL_DIR>` 为本文件所在目录。脚本需要 Bash 和 ripgrep，只提示可能需要复查的词句；命中不是错误，更不是自动替换指令。返回 0 表示扫描完成，非零表示工具或输入错误。缺少工具时人工自查，不为扫描结果改写准确内容。

# Armory 制品管理

只问用法或接口时读取 [docs.md](docs.md)，不进入发布流程。打包、安装验证和发布是不同操作，按当前任务范围选择。

## 移植软件的推荐版本命名

仅对将上游软件移植到 SylixOS 的制品，推荐采用 `<上游核心版本>-sylixos.<N>`，
例如 `3.43.0-sylixos.1`，用于保留上游版本并区分移植修订。原生开发软件及其他
非移植制品按其自身版本策略发布；用户或项目已有明确约定时优先遵循该约定。

以下约定适用于选择此命名方案的移植项目：

- 核心版本取自可复核的上游版本，缺少补丁段时补零（如 `3.43` → `3.43.0`）。不为避开仓库冲突或表示移植修复而递增上游核心版本。
- `N` 是无前导零的正整数，首次移植发布从 1 开始；同一上游版本的后续独立发布递增 `N`，上游核心版本变化后从 1 重新开始。
- 构建日期、提交号和工具链信息记录在发布证据中，不附加到正式制品版本号。已发布历史日期版本保留，不为统一格式自行覆盖、迁移或撤回。
- `sylixos.N` 按 SemVer 属于预发布后缀，排序低于同核心的裸版本；说明中如实表达该语义，按精确版本下载，不能假定 `latest` 自动指向移植版。
- Armory 将仅 `+build-meta` 不同的版本视为等价版本；Tag 是版本的分发别名，不是二进制快照。不得用日期元数据或日期 Tag 代替独立移植修订。
- 打包时核对配置、归档文件名和说明中的版本一致，并校验核心版本与上游相符、修订号有效。

## 当前项目流程

先读项目的 Armory 配置、Makefile、发布脚本与目标配置，核对 CLI --help。包名、版本规则、平台、最低系统版本、文件布局和依赖来自当前项目，不套用 Node 的值；移植软件可参考上述命名建议。

- 打包前核对版本与元数据、已构建架构、预期内容和目标运行库。符号检查遵循项目规范，不强制所有 ELF 使用同一依赖集合。
- 需要 strip 时保留原始符号产物，并选择匹配架构/ABI 的工具。大小变化不是正确性证据。
- 先在临时目录检查归档成员、权限、链接和解包结果，避免意外覆盖；只有项目明确采用根目录安装布局时才准备相应包。
- 安装前确认目标、覆盖范围与回滚条件，检查安装结果并执行项目要求的加载和功能验证；清单存在不等于运行正确。
- 发布须在任务授权范围内，遵循项目 autoPublish 等限制。不能因脚本提供 --force 就把它视为用户授权；发布或 release 脚本也可能修改版本、提交 Git 和创建标签，调用前检查范围。
- 如需改变 CLI 配置，先保存实际旧值，结束后恢复旧值，不假定原值为 false。远端发布可能部分完成，本地回滚不代表远端已撤回，先核对远端状态再决定重试。

报告包版本、架构、实际检查、目标运行和远端发布状态，明确未完成阶段。项目使用 Node 的旧脚本布局时可读取 [armory-node.md](armory-node.md)，仍以当前脚本为准。

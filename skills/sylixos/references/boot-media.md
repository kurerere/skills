# SD 启动盘与启动失败排查

板子上电或复位后启动失败、串口日志停在加载阶段时读取。目标侧命令仍按 [board-operations.md](board-operations.md) 与 [shell.md](shell.md)。

## 先定位失败阶段

按串口日志从前往后分阶段确认，不急着怀疑板卡或镜像：

- loader 阶段（分区表之前的原始写入区）：SPL、FIT 镜像逐项哈希校验输出正常，说明这部分完好。
- 文件加载阶段：`reading <file>` 后打印 `Invalid FAT entry`、实际读出字节数小于文件真实大小，说明文件簇链中途被截断；随后 `Starting application` 跳转即 Synchronous Abort 是拿残缺镜像执行的必然结果，不是新问题。
- 判定方法：拿日志里的 "bytes read" 与文件真实大小比对。两者不等且此前报过 Invalid FAT entry，问题在文件系统不在镜像。

## 关键认知：fsck 通过 ≠ bootloader 可读

FAT32 表项低 28 位是簇链，高 4 位是保留位。操作系统按规范只取低 28 位，简化版 bootloader 可能拿整个 32 位做合法性判断，遇到高 4 位非零或超出范围的值即报 Invalid FAT entry 并截断读取。

断电、热插拔留下的伤可以只在保留位、两份 FAT 不同步、数据误写进 FAT 区这类位置——这类伤不影响按掩码读的操作系统，主机端 fsck 只校验链连通性，照样报 clean。主机上"文件能完整读出"同样不能证明对 bootloader 可读。bootloader 的合法性判定以该版本源码为准。

## 取证

1. 先把启动文件全量备份并记录哈希。
2. 导出该分区的原始镜像（只读，不改盘）。

第 3–5 步可用 `python3 <SKILL_DIR>/scripts/fat_check.py check <分区镜像> --path /<启动文件>` 完成：报告保留位非零的表项、多份 FAT 的差异、按 32 位整值判断时在第几簇截断及约读到的字节数，并给出按掩码重建的 SHA-256。整盘镜像用 `--offset` 指定分区起始字节。脚本只读；手工步骤如下，用于核对脚本结果或脚本不适用时：

3. 解析 BPB 定位 FAT 区与数据区；逐表项检查三类异常：链中间出现空闲值（≤1）或结束标记（≥0x0ffffff8）、保留位非零、多份 FAT 副本不一致。
4. 从目录项起始簇沿链走，找到第一个非法表项，把断点位置换算成字节偏移，与串口日志报告的已读字节数核对——相等即确诊。
5. 离线验证修复方案再写回：按掩码修正表项后沿链重建文件字节，与备份哈希比对。一致说明低 28 位链接本来就完好，只需清位，文件数据可保持不动。

## 修复选项

按当前可用工具与权限选择，不定死某一条：

- 只改 FAT 表：所有表项保留位清零，以活动 FAT 为基准同步其余副本，写回分区镜像。`fat_check.py fix <分区镜像> <新镜像>` 生成这样的副本（以 FAT#1 为准，不覆盖已有文件）；FAT 镜像标志指定了其他活动 FAT 时不要用它。分区表、其它分区和文件数据都不动。写回前必须先在镜像上验证全部链完整、文件哈希一致。
- 重格式化该启动分区再拷回文件：前提是文件已备份并校验，重建后簇链干净。
- 原厂工具重制启动盘：最彻底，布局保证正确。

写回盘后重新抓取 FAT 区确认表项干净、两份一致、链完整，再上板验证；只凭写入命令成功不算修复。

## 边界与预防

- 以上修法只动启动分区。同卡上的根文件系统分区若是私有格式，主机端无法检查；启动恢复后如系统仍异常，用目标系统工具查根分区，不能默认它也是好的。
- 同类卡上的启动文件若由厂商/板载工具写入，保留位带脏可能再次出现；修复只保证当前状态。
- 预防只有一个动作：写完启动盘后正常卸载再断电。0 字节文件、孤儿簇通常是上一次的断电残骸，可作为佐证但不是唯一判据。

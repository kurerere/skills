# ECSD Development Workflow

## 总原则

只面向 SylixOS ARM64。先明确任务边界和验收证据，再实现；先锁定 Bug 根因，再修复；每个阶段都保持可验证、可回滚、可交付。

遵守项目 `AGENTS.md`、领域模型和 ADR。保留用户已有改动，不覆盖无关文件，不使用破坏性 Git 命令，不未经用户确认引入外部库。

## 任务分流

### 新功能或行为变更

严格按以下顺序执行，不跳过中间产物：

1. 明确目标、边界、反例、风险、验收条件和不应改变的行为；需要讨论时使用全局 `$grilling`。
2. 按项目既有约定记录已确认的规格和最高层测试边界。
3. 将工作拆成可独立验证的切片，明确依赖和验收条件，沿用本地任务记录。
4. 使用 `$ecsd-implement` 实现已确认工作，运行聚焦验证与最终回归，检查规范和回归风险。

规格、工单或 seam 尚未确认时，不开始大规模实现。若任务只是文档、诊断性检查或极小的机械改动，说明跳过哪些阶段及原因。

### Bug、崩溃、挂起或性能回退

先建立诊断循环：复现、收集证据、缩小范围、锁定根因、提出方案、补回归测试。未锁定根因不得修复；需要改变修复方向时先让用户决策。

需要调试进程、线程、崩溃或远程状态时使用 `$sylixos-gdb`。需要向板卡上传文件、执行命令或启动程序时使用 `$sylixos-ext-skill`。两者不能用临时自制脚本替代其标准流程。

### 设计、接口或重构

先明确模块职责、依赖边界和外部行为测试 seam；比较候选接口，沿用项目领域术语，需要记录决策时写 ADR。C++ 实现遵循当前项目规范。

## 分支与阶段性提交

### 开始任务

1. 查看当前分支和 `git status`，识别并保留无关改动。
2. 为本次任务新建或切换到 `feat_<简短名称>` 分支；不要把多个无关目标混在同一分支。
3. 记录基线：原版行为、当前测试结果、目标板卡、配置、数据库和可复现步骤。

### 阶段完成

每个已批准工单或完整垂直切片完成后：

1. 检查仅有预期文件变更。
2. 执行该切片的聚焦测试和必要的板卡验证。
3. 检查差异中的规范、规格和回归风险。
4. 只暂存本阶段相关文件，禁止无目的执行 `git add .`。
5. 创建一个小而完整的提交；不要把未验证的半成品提交为完成状态。

提交信息规范遵循 `$commit`。

## 代码理解与索引

在查看或分析项目代码前：

1. 在项目根目录运行 `codegraph sync .`。
2. 仅在首次建立索引、同步失败、索引损坏或大规模结构变更时使用 `codegraph index .`。
3. 优先使用 CodeGraph 定位符号、调用路径和当前源码，再读取必要的局部文件。
4. 先阅读 `AGENTS.md`、相关 ADR、领域 glossary 和既有测试。

JS 行为对齐时按目标模式选择基线：VSOA 使用 JS v1（`main.js`、VSOA 路由和 controller），CRI 使用 JS v2（`maincri.js`、CRI 模块）。执行 CRI v2 平替、gRPC CRI 行为对齐、原版差分或板卡验证时，读取并遵循 `docs/agents/cri-equivalence-workflow.md`。代码优先于文档，遇到冲突先记录并向用户确认。

遵守架构隔离：CRI 与 VSOA 私有头文件不得跨模块引用；`common` 只放无状态纯函数；代码应通过命名和结构自解释，禁止步骤性、装饰性和冗余注释。

## 文档一致性

持续留意实际代码、运行行为与以下项目文档是否一致：`AGENTS.md`、`README.md`、`PROJECT.md`、`CONTEXT.md` 以及 `.agents/` 下的规范、Skill 和参考文档。

发现不一致时：

1. 记录文档路径、原文规则、实际观察、复现步骤和证据来源。
2. 区分文档过期、代码未实现、代码缺陷、环境差异和有意偏离，不以猜测代替事实确认。
3. 在事实确认前，不为了让结果看起来一致而直接修改代码或文档；功能修复仍需遵守 Bug 根因流程。
4. 在阶段总结或最终交付前向用户说明差异、影响范围和建议修改内容，询问用户是否同意更新文档。
5. 只有用户达成一致后，才修改对应文档；文档修改应经过检查并与相应功能变更一起进行阶段性提交，或作为独立的文档提交。

最终报告列出已发现的文档冲突、确认结论、用户决策和是否已完成更新。未获用户确认的文档差异标记为“待确认”，不得静默处理。

## 并行执行

优先并行处理互不阻塞的工作：代码阅读、原版行为分析、测试设计、不同模块的实现和静态检查可以并行。

并行任务必须满足：

- 每个任务有明确的写入范围，避免两个任务修改同一生产文件或同一测试用例。
- 每个任务交付代码、测试、证据和未解决风险，而不是只返回结论。
- 构建、集成、冲突处理和同一板卡上的服务启停保持串行。
- 发现任务边界重叠时先暂停扩展改动，重新划分范围。

## C++ 实现与构建

具体实现遵循 `$ecsd-implement`，按项目规范编写 C++，在既有外部行为边界验证改动。优先在既有最高 seam 编写外部行为测试，避免为测试暴露不必要的内部实现。

构建只能通过项目根目录 Makefile，并按标准顺序执行：

```text
make format
make config
make build
```

不得直接调用 CMake、Ninja、编译器或绕过 Makefile 的清理命令。构建失败先分析原因，不得换用底层命令掩盖失败。最终报告列出实际执行的 Makefile 命令及结果。

## SylixOS 板卡验证

板卡上传、Telnet、权限、超时和远程结果确认遵循 `$sylixos-ext-skill`；GDB 连接、符号、线程和远程调试遵循 `$sylixos-gdb`。每个任务首次操作板卡前，先让用户确认目标地址、用途，以及查询、上传、启停程序、修改数据和重置环境的权限；历史任务授权不延续。授权范围变化或新增目标时再次确认。确认前只进行本地工作。

同一板卡上的服务启停和运行时测试串行。只有本任务明确授权的独立只读检查和上传可以跨板卡并行。需要隔离原版与新版时，分别确认数据库、数据目录、端口和测试进程，避免服务与测试互相干扰。

## Bug 调试与 GDB

使用 `$sylixos-gdb` 执行崩溃、挂起、线程和远程状态诊断，遵循其动态端点选择、匹配符号、只读诊断和授权规则。项目流程只要求保留可复现步骤、原始回溯、线程状态、修复前后差异和回归证据。

## 测试与差分证据

按以下层次推进测试：

1. 聚焦外部行为测试：覆盖本次切片的正常、边界、错误和并发行为。
2. 目标板运行的模块/集成测试：确认 SylixOS runtime、数据库、文件系统和网络行为。
3. 原版/新版同输入差分：记录请求、响应、状态迁移、持久化结果和错误语义。
4. 全量回归：所有功能切片完成后只执行一次完整测试闸门，并保留原始输出。

为每项差异标记“已对齐”“有意差异”或“待处理”，不得把未解释差异当作通过。遇到测试失败先区分代码失败、测试环境冲突、板卡状态和部署问题。

涉及覆盖率插桩构建、板卡采集、守护进程 Dump 或数据导出时，遵循 `docs/agents/sylixos-coverage.md`。

## 最终交付与用户自测

只有在规划的全部功能已经开发、聚焦测试、完整回归、代码审查和原版/新版差分审计完成后，才进入最终交付。

最终报告必须包含：

- 已完成的功能和仍存在的限制。
- 实际提交、构建、部署和测试命令及结果。
- 本任务授权板卡的角色、配置、进程和验证证据。
- 未解释差异、已知风险和回滚方式。

随后明确告知用户手动自测方式和步骤，至少包括准备条件、测试顺序、预期结果、日志位置和失败时需要收集的信息。通知用户开始自测，并明确鼓励用户即使没有发现问题，也提供完整的自测过程日志，以确认实际行为符合预期。

用户自测完成并反馈日志后，再关闭任务或宣布最终完成；没有用户自测反馈时，状态应标记为“自动化验证完成，等待用户自测”。

# Coding

## 先确定要改的行为

1. 读取适用的仓库约定、构建配置和已有测试。沿实际调用路径定位入口、行为归属和现有实现，找到可运行的最小验证命令。优先复用项目已有的实现和测试设施。
2. 把需求落到可观察的输入、结果或状态变化。区分本次要改变的行为与现有调用者依赖的行为。仓库证据不足且歧义会改变结果、兼容性或规则归属时，再向用户确认。
3. 按改动选择下面的路径。一个任务同时有行为变更和重构时，把它们分开验证。

| 改动 | 执行动作 |
| --- | --- |
| 新功能或改变可测试的行为 | 从正常入口写一个聚焦的行为测试，运行并确认它因目标行为缺失而失败。做足以满足该行为的最小实现，重跑同一测试，再在绿灯下按需重构。一次推进一个行为。读 [TDD](references/tdd.md)。 |
| 修 bug | 先用可信的输入复现。定位到足够小且稳定的入口后，用同一用例证明修复前失败、修复后通过。排查中的假设用观测来验证。读 [TDD](references/tdd.md)。 |
| 纯重构 | 先运行相关测试取得绿灯基线。仅在关键现有行为缺少保护时补刻画测试，确认它在改动前通过。每个结构改动后复跑同一组验证。 |
| 只评审 | 沿入口核对行为、失败路径、测试与兼容性。给出有证据的具体问题、触发条件和影响。 |
| 新增、修改或澄清业务规则 | 业务约定本身变化，或术语、规则归属、状态转换或一致性边界还需确定时，在对应编码路径中同时读 [DDD](references/ddd.md)。仅修正一条已明确规则在现有归属中的实现时，按缺陷修复路径处理。只做数据读写且沿用既有规则时，复用现有流程。 |

## 写出容易读和容易改的代码

- 沿用项目命名、错误处理和接口习惯。名字表达意图，同一概念沿用同一术语。让输入、输出、副作用和资源归属在调用处可见。
- 函数围绕一个可描述的职责组织。先保持逻辑就近，只有拆分能减少认知负担、集中同一条规则或明确依赖时才提取。行数、嵌套和参数个数是检查信号，拆分看职责。
- 复用有相同语义和演进原因的现有逻辑。引入接口、值对象或设计模式前，指出它解决的具体问题。对于推测性的边缘情况，先用可触发的失败路径说明需求和成本。
- 让常见路径直观，让错误和清理路径完整。改变已有接口或存储行为时，检查旧调用者、旧数据以及失败后重试的结果，范围以受影响的行为为准。
- 只为代码难以表达的意图、约束或取舍加注释。提交前回看改动，移除临时诊断和无用代码。需要判断职责、抽象或依赖方向时读 [干净代码与 SOLID](references/clean-code.md)。

## 按改动读取语言参考

仅在涉及相应语言时读取。版本和验证入口以项目配置为准。

- [C](references/c.md) 包含缓冲区契约、资源所有权与失败清理。
- [C++17](references/cpp17.md) 包含 RAII、值语义、生命周期与异常安全。
- [Go](references/go.md) 包含错误契约、上下文、并发生命周期与表驱动测试。
- [JavaScript 和 TypeScript](references/js-ts.md) 包含运行时边界、类型收窄、异步错误与状态建模。

## 用实际结果验收

先跑聚焦检查，再跑受影响的测试、构建或静态检查。确认用例检查了预期行为，且相关旧用例仍然通过。测试环境受阻时，执行能覆盖同一行为的最小复现或最接近的检查，并说明实际命令、结果及仍待验证的部分。只有观察到目标失败和随后通过时，才把结果描述为红灯转绿灯。

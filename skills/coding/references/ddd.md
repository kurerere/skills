# 领域驱动设计

## 先确认术语和规则归属

1. 读已有词汇表、需求、测试和实际调用入口。写清谁发起什么操作、何时允许、失败时应保留什么状态。用同一套领域词汇命名代码和测试。
2. 如果同一个词在不同流程中含义不同，按能力、规则归属和生命周期确认限界上下文。例如销售关心商品定价，仓储关心商品的库存和出入库。两处可以共享标识，各自持有支持本流程的状态。
3. 仅在改动跨越上下文时梳理关系。明确哪一侧拥有事实、另一侧通过什么契约取得它、术语在哪里转换。复用仓库现有记录方式。证据冲突且选择会改变行为时，带具体用例确认业务含义。

## 从不变量选实现

写下每条必须成立的业务规则。找出哪些操作可能破坏它、做出判断需要哪些状态、失败时允许提交什么。然后选能守住规则的最小方案。

| 现象 | 可选实现 |
| --- | --- |
| 输入格式或范围要求 | 在输入边界校验。若一个概念的校验和行为在多处复用，考虑值对象。 |
| 单步骤数据变更或唯一性要求 | 沿用现有流程、事务或数据库约束，由拥有权威状态的一侧保证。 |
| 对象靠标识延续，行为随状态变化 | 用实体或模块内的状态和操作表达生命周期。将转换与约束放在同一处。 |
| 同一个操作必须让多个对象共同满足规则 | 评估聚合。只纳入决定和提交该规则所需的状态，让根或模块入口统一维护不变量。 |
| 规则横跨独立边界 | 先确定权威状态和允许的一致性时机，再决定是否使用现有事务、显式协调或事件。 |

值对象按值比较，构造时建立有效状态。实体靠标识区分，允许受控的状态变化。聚合范围由需要一起保持的一致性决定。仓储、领域服务和事件分别在出现明确的存取、策略或事实传播需求时引入。查询和展示所需的数据可按读侧需求组织。

## 用状态变化验证模型

对规则写出允许和拒绝的例子，检查公开入口返回的结果及操作后的可见状态。先验证候选状态再提交，或用现有事务同时保护多步变更。例如，订单加一项会超出总额上限时，测试应检查返回超限错误，且订单仍保留原明细和原总额。

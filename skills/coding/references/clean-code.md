# 干净代码与 SOLID

## 命名和结构

从调用处看代码。让操作名表达调用者想完成的事，返回值和错误让调用者能作出下一步决定。业务名称沿用仓库词汇。同一种错误、缺省值和资源所有权沿用同一套约定。

当一个函数同时判断规则、管理资源和格式化输出时，先找最容易独立变化的职责。提取后调用处应更易读，且该逻辑只需在一个地方维护。短而连续的局部操作可以留在一起。用提前返回处理明确的退出路径，保留有助于表达互斥分支的结构。

## 用 SOLID 检查实际改动

| 原则 | 在改动中检查 |
| --- | --- |
| 单一职责 | 哪些规则会因不同需求而改变？反复改动不同职责时，按变化原因拆分。 |
| 开闭原则 | 已出现的同类扩展是否每次都要改多处？先把稳定规则和变化点放在清楚的位置，再决定是否引入扩展点。 |
| 里氏替换 | 调用者依赖的前置条件、结果、错误和副作用在替换实现时是否仍成立？必要时用相同的契约用例验证实现。 |
| 接口隔离 | 调用者需要哪几个操作？接口按实际使用方的职责划定，维持实现所需的最小契约。 |
| 依赖倒置 | 高层规则是否要知道数据库、网络或框架细节？需要隔离时，让规则一侧描述所需能力，由边界实现。依赖简单时可以直接调用。 |

## 决定何时抽象

- 当重复代码维护的是同一条规则、修改时总要同步，才考虑集中。几段看起来相似但归属不同的代码可以各自演进。
- 当数据与校验、等价关系或业务行为总是一起出现，考虑值对象或受校验的构造入口。普通参数按现有约定处理。
- 当分支代表稳定的有限状态，清楚的条件或 `switch` 便于审阅。只有同一类变化反复导致多处分支同步修改时，才比较表驱动、策略或多态的成本。
- 保持跨模块接口小而完整。优先复用已有依赖边界，让调用者通过正常入口使用功能，降低内部重构的影响范围。

改动结束后，检查新增类型、函数、配置和依赖各自解决了什么问题。遇到只能用未来假设解释的抽象，按当前需求简化。

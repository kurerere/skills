# 测试驱动开发

## 一个行为一个循环

1. 选一个能观察到变化的例子。先找现有 API、命令、模块入口或测试夹具。选能捕获目标回归且运行足够快的入口。预期值取自需求、已知结果或独立算出的例子。
2. 写并运行一个聚焦测试。看清断言失败的原因。若测试提前通过，检查行为是否已存在、输入是否走到目标分支。若运行止于构建、环境或夹具错误，先处理这些障碍。新增接口需要先让测试能调用它时，可用最小声明或占位使测试跑到行为断言。
3. 做让当前行为通过的最小实现，再跑同一个用例。测试预期有误时根据需求纠正，并重新确认它能够捕获目标缺陷。
4. 在绿灯下清理重复、命名或结构。需要进一步覆盖时，根据上一个用例的结果选下一个行为。最后运行受影响的检查。

对于跨组件功能，第一个用例选一条可运行的最短完整路径，尽早验证关键连接。后续边界和错误用例放在最贴近其风险的入口。一个行为可以包含相关结果，例如返回业务错误并保留原状态。

## 选择测试边界

- 领域规则或算法通常用模块公开入口和真实的领域对象。涉及序列化、持久化、事务或协议时，选能观察到相关失败的集成测试。
- 用项目现有机制替换网络、时钟等难控制的依赖。断言结果、状态或协议要求的副作用。只有交互顺序或次数本身属于契约时，才把它写进断言。
- 测试名写清触发条件和结果。设置步骤只保留理解用例所需的输入。对有代表性的边界值、旧数据和错误路径加覆盖，以实际变更风险为准。
- 纯重构先用现有测试建立绿灯。覆盖缺口处可写刻画测试来记录已确认需要保留的行为，改动前后均应通过。

## 反馈环受阻时

目标依赖板卡、外部服务或暂时不可用的环境时，先用现有夹具、最小复现或针对同一契约的检查缩短反馈环。只有能实际观察到该用例在目标行为上失败才记为红灯。最终区分跑过的验证与待在目标环境执行的验证。

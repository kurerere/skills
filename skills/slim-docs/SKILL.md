# 主干文档：只留代码说不出的信息

写给下一个会话的 AI：给出发点和方向，不给细节——细节它从代码现取。没有文档它会去查代码，文档写错它会照着错的做；所以宁可少写，不可写细。

> **适用范围**：本技能仅用于仓库内长期协作文档（如 `AGENTS.md`、ADR、README 导引）。面向运维与外部的操作手册、部署 SOP 与接口文档保持独立完整，不在此处删减；已安装 `tech-docs` 时可按其规范编写。

精简保持原文的事实与意图，约束的对象、范围、适用条件和必要理由不变。当前实现或使用场景不能自行升级为长期禁令；原文没有说明的归属或理由，保留已知事实与疑问，不补成用户已确认的决定。

## 写入前三问

一条信息想进长期文档，先过三问，有一问答不上就不写：

1. **AI 只看代码能不能推出这条？** 能 → 不写。
2. **哪些内容应由测试、类型、lint 或 CI 验证？** 将验证落实到对应机制；主干仍保留用户意图、硬约束及其必要理由，不复述实现细节。
3. **过期那天谁会知道？** 答不上 → 不进长期文档，写进 commit message、PR 描述或 issue——随一次改动翻篇的地方。

## 什么算主干

只写 AI 从代码推不出、或会推错的东西：

| 类别 | 写什么 | 为什么代码说不出来 |
| --- | --- | --- |
| **意图** | 用户要做什么、已明确不做什么 | 代码只有现状，没有取舍 |
| **决策理由** | 为什么选 A | 代码只看得见选了 A |
| **否决项** | 放弃的方案及原因 | 不写，下个 AI 会再提议一遍 |
| **硬约束** | 不得改变的行为、对外承诺、兼容底线 | 测试未必拦得住 |
| **教训** | 踩过的坑、版本陷阱 | 代码里看不出来 |
| **指路** | 入口、权威来源在哪 | 一句话指路，不复制内容 |

意图、硬约束、指路必须照办；决策理由、否决项、教训是当时的判断，防止重复提议已否决的方案，但不保证今天仍成立。与当前代码或新证据冲突时，指出冲突，不沉默服从。

## 什么不算主干

以下信息不落入长期主干，出现即删：

- **不写代码行号**：如 `见 service.go 第 45 行`，代码一改立刻失效。
- **不贴源码实现**：最多放调用命令、最小调用示例或函数签名，不贴完整函数体。
- **不列易变文件树**：用一句话指路（如“核心服务收敛在 `src/services/`”）。
- **不抄字段表与配置全表**：代码与配置文件是唯一权威，现查比抄进文档准。
- **不留过程流水账**：留在 commit message 和会话里。

判据：这段是帮 AI 对齐方向，还是帮它省得再查？后者不写——省一次查，赌一次错。

## 落在哪

### 1. 项目协作主干 → `AGENTS.md`
长到需要目录，先怀疑混进了代码细节：

按项目需要组织目标、已确认的约束、验证命令和必要指路。同一约束只维护一处，避免在意图、边界等章节中再次改写。

### 2. 重大决策与否决 → ADR
一份一个文件，按需要写清背景、依据、决策与代价：

```markdown
### ADR-001: 决策标题（如：改用 Redis 管理分布式会话）
- **状态**：已采纳（或已否决 / 已废弃）
- **背景与依据**：遇到什么问题（如多节点部署内存会话无法共享）
- **决策**：选了什么方案
- **否决与代价**：否决了方案 X（原因 Y），代价是需额外运维 Redis
```

### 3. 其他分工
- 功能需求 → 项目已有的需求入口；已安装且显式调用 `refine-requirements` 时按其约定维护，编号按引用需要设置。
- 临时草稿、过程笔记 → 留存会话或 `.scratch/`，任务收尾时删除或提炼进提交信息。

## 保持干净与自检

- 改动让既有文档某条过时时，在同一提交里改它或删它。
- 重复描述实现的内容移交代码或验证机制；用户意图、硬约束及必要理由仍保留在主干。
- **收尾自检**：
  - [ ] 没有写死代码行号、没有大段粘贴源码实现
  - [ ] 没有文件清单、接口字段表进长期主干
  - [ ] 决策与否决项写清了当时依据，而非空洞结论
  - [ ] 被本次改动推翻的文档条目已改或已删
  - [ ] 主干简短、入口清楚，没有为压缩篇幅丢失必要信息

## 与其他技能的关系

- `refine-requirements`：显式调用时维护薄需求层，记录目标行为、必要边界和未决问题，不扩写配套材料。
- `tech-docs`：手册与 SOP 保留读者执行所需信息，按任务选择结构；本技能只管仓库内长期协作主干。

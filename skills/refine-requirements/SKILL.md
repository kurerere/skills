# 薄需求层

仅在用户显式调用 `$refine-requirements` 或明确指定本技能时执行。

**让实现者知道要做什么、必须守住什么、还有什么没定。** 需求文档保留影响实现结果的意图和边界，具体实现交给代码阶段。薄是少一层重复表达，不是省掉关键条件。

## 内容边界

- 保留目标、可观察行为、重要失败与兼容边界，以及用户或外部系统明确施加的约束。已有代码可以说明现状，不能代替需求决定未来行为。
- 用户指定的协议、技术、接口路径或数据格式可能就是需求约束，照实记录；不由技能擅自选择实现方案。
- 不复制代码可查的模块清单、字段表和调用流程，不自动衍生设计文档、任务清单或测试计划。需要指路时链接权威来源，不再抄一份。
- 同一事实只在一处作权威表达。默认不叠加需求总表、逐条正文、流程图和脑图；图或例子只在能消除歧义时加入。

## 从想法到可执行的需求

先理解用户意图，查项目约定、相关代码和已有需求，确定哪些行为需要改变、哪些必须保留。能从现有材料确认的事情自行确认。

围绕会改变结果或边界的缺口提问。已有授权范围内的实现选择留给实现者；尚未确认的主干需求记为待问，不靠猜测定稿。提出异议时说明依据，用户接受的权衡只保留决定及必要后果，不保存对话过程。

选择足以让实现者行动的最小结构。默认一份 Markdown，位置沿用项目约定，没有约定时用 `docs/features/<slug>.md`。已有需求就在原文更新，不为一次澄清另建一套材料。

需求涉及多条行为或会被引用时给稳定编号；已定、自由、待问的区别要清楚，可采用示例中的标记，也可沿用项目格式。“自由”只界定有意义的选择空间，不逐项列出所有实现细节。

维护时用新决定替换旧表述，回收已解决问题与失效假设；仍被引用的编号不随排版调整而重排。历史理由已有提交或决策记录时链接即可，不在需求里逐轮累积版本。

## 交付前判断

实现者能否区分必须遵守的行为、可自行选择的部分和仍需确认的问题？关键条件与失败结果是否足以判断？是否丢掉用户指定的约束，或重复描述了代码和其他文档？

若这些问题已清楚，不再为了填模板加章节。按需参考 [条目与边界](references/rules.md) 和 [最小示例](references/template.md)，不要求固定章节、句式或图形。

可选扫描：`bash <SKILL_DIR>/scripts/check.sh <需求文档>`，`<SKILL_DIR>` 为本文件所在目录。需要 Bash 和 ripgrep，只提示模糊表达和示例格式中可能漏写的内容；不识别语义，也不要求文档迁就它的格式。返回 0 表示扫描完成，非零表示工具或输入错误；缺工具时人工自查即可。

# 薄需求层

仅在用户显式调用 `$refine-requirements` 或明确指定本技能时执行。

**先明确要什么，再在这些边界内实现。** 主干需求说明要一个什么东西、达到什么目的、谁在什么场景下使用，以及必须守住和不能触碰的边界。关键要求应能判断是否满足，结构和篇幅按任务选择。

REQ 记录用户要求，代码与测试承载细化需求。模块划分、内部数据结构、算法和具体处理流程由实现阶段决定，不再转述成另一套文档。用户明确指定的技术、接口路径、格式或兼容要求仍属于主干约束，应保留。

## 需求入口

新建需求放在 `.requirements/REQ-<主题>.md`，例如 `REQ-技能管理.md`。每份对应一个能独立理解的需求主题，持续原地更新；不按模块、开发步骤或讨论轮次拆文件。用户明确指定其他位置时遵从；已有同主题需求先确认入口，避免新旧文档并存。

主题较多、文件名不足以定位时，用 `.requirements/README.md` 列主题链接、一句话范围及必要的依赖关系。索引不复述需求；主题少时可以省略。

在项目 `AGENTS.md` 中留需求入口与维护约定即可，不把需求内容再抄进去。没有主干需求需要记录时，不为凑目录创建占位文件。

## 按需理解与决策

先查项目约定，从索引或文件名定位本次任务相关的 REQ，再沿明确的依赖补读，不默认加载所有需求。相关代码用于理解现状与可行性，不代替用户决定目标。

实现选择不改变目标、对外行为或关键约束时，由模型自行判断。只对会改变这些要求的缺口追问；模型提出的建议在得到确认前保留为建议或待问，不能写成既定需求。不必逐项给实现细节标“自由”。

跨主题约束确定一个归属，其他主题引用它；同一事实只在一处维护。跨主题引用容易混淆时给关键条目稳定编号，小需求用自然语言即可。图与例子只用于消除歧义，不叠加总表、正文和图重复描述。

## 变更与实现反馈

用户改变决定时更新原 REQ，检查受影响的主题、边界和未决问题，替换旧表述。只有旧行为仍需兼容时保留其适用范围；历史过程留在 Git，已解决的问题与失效假设及时回收。仍被引用的编号不随排版调整而重排。

**代码偏离 REQ 时，先判断缺陷或需求变更。** 修正实现，或向用户确认新的要求；不能为迁就现有代码自行改写 REQ。代码与 REQ 相符时，也不把实现细节倒灌进主干。

实现完成后对照相关 REQ 检查目标与约束，验证落实到代码、测试或实际操作结果。交付时说明未满足和未验证的部分，不默认再生成逐条复述需求的验收文档、追踪矩阵或测试计划。

## 写作与交付

从用户意图中提取目标、目的、使用者与场景、必须遵守和明确禁止的行为，以及影响方向的未决问题。只补影响理解和判断的内容；能区分要求、自由选择与待问事项即可，不要求固定章节、句式或状态字段。

按需参考 [条目与边界](references/rules.md) 和 [主干示例](references/template.md)。交付前看是否丢失关键约束、混入未经确认的决定，或复制了代码与其他主题的内容。需求写清即可交付，不为形式持续扩写；后续获准实现时按相关 REQ 推进。

可选扫描：`bash <SKILL_DIR>/scripts/check.sh <需求文档>`，`<SKILL_DIR>` 为本文件所在目录。需要 Bash 和 ripgrep，只提示模糊表达和示例格式中可能漏写的内容；不识别语义，也不要求文档迁就它的格式。返回 0 表示扫描完成，非零表示工具或输入错误；缺工具时人工自查即可。

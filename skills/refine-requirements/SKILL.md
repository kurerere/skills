# refine-requirements

仅在用户显式调用 `$refine-requirements` 或明确指定本技能时执行。

帮助用户从初步想法创建需求，或补全已有需求。文档应让读者看清功能与现有系统的关系，区分已确认的要求、实现者可自行决定的部分和仍需用户回答的问题。

## 产出

一份 markdown，落在项目里。同一份文件有两个阅读路径：

- **人**：全局描述 → 全景区图 → 需求脑图，抓全貌
- **人和 agent**：编号需求条目，精确执行

由此得出一条硬规则：**任何事实都不能只活在散文或图里**。散文只解释条目，图只呈现条目；图和正文冲突时，以正文条目为准。只活在散文里的约束，agent 会当成建议；只在图里的分支，agent 会漏掉。

只写需求层。不写实现方案、文件路径、代码片段、技术选型、任务清单、测试方案——这些在代码里读得出来，写进来只会过时。

## 流程

### 1. 让想法倒完

不打断、不在中途追问。听完全部再动手，不清楚的先记下。

### 2. 自行调研

能自己查的一律不问用户：

- 项目约定：`AGENTS.md`、`docs/agents/`、`CONTEXT.md`、`.scratch/`、既有 spec
- 相关代码：这个功能会碰到哪些现有模块、它们现在怎么工作、哪些既有行为必须保持不变
- 术语：项目里已有的叫法，不要另造词

### 3. 出草案

先画全景区和需求脑图，再补文字。凡是没有确切依据的判断，都显式落进「假设」或「待问」，不要写成陈述句。

### 4. 只对高风险项追问

只问主干需求和边界。停止判据：**新得到的答案不再改变文档里任何一条需求、边界或影响面**。

答案与调研事实冲突、或明显不合理时，直接质疑并说明理由。用户坚持，就照他的写，同时把「你的质疑 / 用户理由 / 后果 / 何时该回头看」记进「已接受的权衡与后果」。问到没有确定答案的，进「未决问题」，不要自己编一个合理答案填坑。

### 5. 落盘

位置优先级：项目既有约定 > `docs/features/<slug>.md` > 问用户（给出建议和理由）。

### 6. 自检后交付

- [ ] 没有实现细节：无文件路径、代码片段、技术选型、任务清单、测试方案
- [ ] 每条需求有稳定编号（FR-01…）、单一行为、可判定
- [ ] 每条需求和开放点标了三态：`已定` / `自由` / `待问`
- [ ] 没有禁用词（清单见 `references/rules.md`）
- [ ] 图里没有正文没有的信息
- [ ] 影响面写清了「必须保持不变的既有行为」
- [ ] 每条假设都写了「若不成立会怎样」
- [ ] 术语用的是项目既有叫法

然后把文档给用户过目定稿。

## 文档骨架

十三节，空节可省。完整模板、每节写法、Mermaid 片段见 `references/template.md`。

1. 一句话摘要
2. 全景区 —— 现有 / 改动 / 新增 / 不动 分区上图，附影响面
3. 需求脑图
4. 需求总表 —— 编号 / 一句话 / 三态，给扫读和 agent 索引
5. 问题与价值 + 成功标准
6. 范围 —— 做什么 / 明确不做 / 与相邻功能的边界
7. 功能需求 —— 按组：流程图 + 编号条目 + 关键例子
8. 交互与状态 —— 时序图、状态机图，按需
9. 边界情况与失败行为
10. 假设 —— 每条带后果
11. 未决问题
12. 已接受的权衡与后果 —— 决定 / 质疑理由 / 用户理由 / 后果 / 何时回看
13. 术语 —— 含「代码里对应什么」

## 写法要点

- 需求句式：「当 X 时，系统应 Y」「在 X 期间，系统应 Y」「若 X，则系统应 Y」「系统不得 Y」
- 一条需求一个行为，条件写全，不给实现留缺口
- 三态标记最值钱：agent 分不清「没写」是疏忽还是授权，于是要么乱猜要么过度收敛
- 句式表、禁用词、条目与例子格式，全部见 `references/rules.md`

## 不要做

- 不写实现方案、不猜文件路径、不拆任务、不给测试方案
- 不调用、不依赖任何其他技能；产出物自成一体
- 不替用户决定主干需求和边界——那是要问出来的
- 信息不足时不编造答案

# 写法规则

## 一、需求句式（EARS 中文版）

条件分支正好对应流程图里的判定节点，所以每条需求都要能用这几种句式写全。

| 类型 | 句式 | 例 |
|---|---|---|
| 普适 | 系统应 〈行为〉 | 系统应保存最近 3 次失败记录 |
| 事件驱动 | 当 〈触发〉 时，系统应 〈行为〉 | 当上游返回 5xx 时，系统应重试 |
| 状态驱动 | 在 〈状态〉 期间，系统应 〈行为〉 | 在退避等待期间，系统应拒绝新请求 |
| 可选特性 | 若启用 〈特性〉，系统应 〈行为〉 | 若启用重试，系统应记录每次尝试 |
| 异常行为 | 若 〈异常触发〉，则系统应 〈行为〉 | 若重试次数达到上限，则系统应返回原始错误 |
| 否定 | 系统不得 〈行为〉 | 系统不得对非幂等请求重试 |
| 保持 | 系统应继续 〈既有行为〉 | 系统应继续按原顺序投递消息 |

写不出上面任何一种句式的需求，通常是还没想清楚。

## 二、三态标记

每条需求、每个开放点都必须落在三态之一。缺了它，实现者无法区分「没写」是疏忽还是授权。

- `已定` —— 需求明确，实现者不得偏离
- `自由` —— 明确授权实现者决定。要写清自由的范围和必须遵守的约束（例：`自由: 退避算法自选，但总时长不得超过 30s`）
- `待问` —— 必须回到需求方确认，实现者不得自行拍板

## 三、条目格式

```
FR-03 [已定] 当上游返回 5xx 时，系统应重试，最多 3 次。
  例：上游连续 3 次返回 5xx → 第 4 次不再重发，向调用方返回原始错误。
  反例：上游返回 400 时不重试。
```

- 编号稳定，一经分配不再变；下游任务、提交信息、测试用例都引用同一个编号
- 一条需求只写一个行为。「并且」「同时」「以及」连接两个动作时，拆成两条
- 每条需求至少给一个可判定的结果；做不到就是还没写完

## 四、例子与反例

- 一个具体例子（输入 → 可观察的输出）胜过三句形容词
- 关键需求配一个**反例**，说明「不该发生什么」。只给正向例子时，实现者会顺手把边界外的情况也做了
- 例子里不写实现细节，只写可观察行为

## 五、假设的格式

```
A-02 假设上游支持幂等键。若不成立：重试会产生重复写入，第 9 节的非幂等边界需要改为默认不重试。
```

没有「若不成立会怎样」的假设是哑雷，不算写完。

## 六、禁用词

不给数字，不许用。

**中文**：灵活、易用、友好、足够、适当、合理、尽快、快速、高效、稳定、健壮、可扩展、安全、直观、尽量、最大限度地、等等、诸如此类、以及/或者、必要时、视情况而定、正常、良好、完善、优化

**英文**：flexible, easy, sufficient, adequate, user-friendly, usable, appropriate, fast, quickly, robust, scalable, secure, intuitive, minimize, maximize, portable, lightweight, efficient, seamless, etc., and/or, if required, as appropriate, if possible, when necessary

## 七、其他措辞规则

- 比较级不给数字不能用：更快、更小、更好
- 全称词不给数字不能用：所有、任何、从不、总是、唯一
- 角色写具体是谁。「用户」「系统」指代不清时，换成具体角色
- 不用模糊指代：它、该模块、相关部分
- 不写逃逸条款：如果可能、酌情、在需要时

## 八、写前自检

- [ ] 每条需求都能对上第一节的某一种句式
- [ ] 每条需求有编号、有且只有一个行为、可判定
- [ ] 每条需求和开放点有 `已定` / `自由` / `待问`
- [ ] 关键需求配了反例
- [ ] 每条假设带「若不成立会怎样」
- [ ] 运行 `bash <SKILL_DIR>/scripts/check.sh <需求文档>`，逐处处理禁用词、缺三态和缺后果的命中
- [ ] 没有实现方案、文件路径、代码片段、技术选型、任务清单、测试方案
- [ ] 图和散文里没有正文条目之外的独立事实
